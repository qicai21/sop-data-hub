## 0. 执行摘要（先看这个）

| 问题 | 结论 |
| --- | --- |
| Codex 说「小 bug、系统正常」，你感觉没自动化——谁对？ | **两边都有一部分对。** 进程与 pytest 大体绿；但按你定义的「自动化达标」，**核心发运链仍经常靠个案止血**，未达到「一周零人工纠错」。 |
| 大量工单是否「真解决」？ | **多数是「当次事件处理完」**，不是「根因类缺陷闭环」。同类主题在 7 月内反复开单。 |
| 工单数量意味着系统多烂？ | 部分是正常演进/补录/费用迁出；**真正可怕的是卡发运主题的复发率**，不是纯数量。 |
| 自动化真实水位（按你的尺子） | 中唐/吉林/朝钢：**能自动跑通成功样例，但多 lot / 货运补全 / 计数语义仍脆**；九三：**入库同源，交付物靠看板+手核，且仍有路由类事故**。整体约 **65%–75% 半自动**，不是「已自动化完成」。 |
| 测试 | **体量大（约 564 passed / 1 failed）**，对单点补丁有效；**对「多入口同规则」与「真实多日累积数据错误」覆盖不足**。 |

**一句话**：这不是「工单写了已处理就是修好了」的系统，而是 **「每票个案修好 + 规则表/字段兼容不断打补丁」** 的系统；自动化骨架在，**确定性规则未在所有入口统一执行**，所以体感仍是半自动。

## 1. 评审口径（用户定义，已冻结）

### 1.1 自动化达标（客户交付三项目：中唐 / 朝钢 / 吉林）

Live Service / Text Watch / WX OPS 盯到检装车或出港计划后，应按项目 SOP 自动完成：

识别 → 建/匹配放货批次 → 95306 对齐 → 幂等入库 → 发运报表（朝钢含上传）→ 发群  

**允许人工的窄口**（其余人工 = 未达标）：

- 新船名首次接入  
- 同船多 lot 且 **未** 配置显式优先  
- 检装 vs 95306 **车数级**冲突且无法清晰分组  
- 缺关键货运信息（计划号/回运计划号/订单识别号等）  
- 明显超发（&gt;500t 不合理；&lt;500t 可接受）  

**明确不算成功**：货运已抓到不回填、已设优先仍 pending、wagon 对但看板错、JSON 已写清实装/排车下游混乱、95306 已制票却不往下走。

### 1.2 九三

- 底层抓取/同步/入库与上同质；散粮 `wagon_shipments`，箱 `wagon_container_shipments`  
- **不**要求发客户发运报告  
- 交付物：循环运输状态；看板 **「大豆循环现状」**；并定期手核库表 vs 项目人员报告  

### 1.3 结案标准

根因分析 + 测试 + 改代码/数据 + **业务结果真修好** + 该重启的服务已重启。  
仅「pytest 绿 / 进程在」不够。

### 1.4 禁止操作（本评审已遵守）

默认可查不可改主事实表；`rail95306` / `wx-ops-agent` 默认不动。

### 2.4 「已处理」可信度模型

本评审将结案分为三档：

| 档 | 定义 | 在本仓的常见形态 |
| --- | --- | --- |
| **A. 当次闭环** | 该票数据修好 + 该次 Excel/上传发出 | 多数 7 月工单 |
| **B. 入口级根因闭环** | 同一调用链以后同类输入不再炸 | 部分匹配/守卫测试覆盖到的点 |

**当前以 A 为主，B 零星，C 不足。**

## 4. 是否「such amount of problems 都解决了」？

### 4.1 直接回答

**没有。**  
更精确：

1. **大量工单的「当次症状」被处理了**（数据补录、单票发出、局部 if 修补）。  
2. **一类根因未收敛**：多入口规则不一致、字段双写、多 lot 满量策略、事件级取数边界。  
3. **费用类工单**不应再计入 sop 自动化失败率（已迁 `fee_manager`）。  
4. **补录类**解决了历史，不增加「自动能力」。  
5. **归档缺失**放大了「问题没解决」的观感，也掩盖了真实未闭环项。

### 4.2 复发铁证：优先级「三连补丁」

```text
2026-07-12  中唐同船多 lot 误配 lot1          → 已完成（需重启 text-watch）
2026-07-18  显式 priority 接到 match 主链      → 已处理
2026-07-19  infer 同分仍不读 priority          → 已完成
```

这不是三个无关 bug，而是 **同一产品规则在多个代码路径的泄漏**。  
只要还有第三条路径（例如文本触发、95306 合成候选、九三默认船解析），就会出现第四张工单。

同类模式还见于：

- 宝丽 **半窗误发 / 旧幂等键重复发 / enriched 不推进**（发送与状态机边界）  
- 九三 **多 loading + 默认船兜底**（7/18 误挂勇气）  
- 吉林 **串旧趟 / 分票不变量 / 箱级事实源**（计数与归属）

### 4.3 与 Codex 汇报的落差

| Codex 常见证据 | 是否充分 |
| --- | --- |
| pytest 绿 | **不充分**（见 §6 仍有失败；且补丁测不等于 E2E） |
| 进程在跑 | **不充分**（live-service / text-watch / wx-ops 当前可见在跑） |
| 本单 Excel 已发 | **仅证明当次 A** |
| 用户确认某批船对上 | **B 的必要条件**，不能推广到全项目 |

你的结案标准本身是对的；问题在于 **结案粒度停在「票」而非「规则面」**，工单厚度必然上升。

## 5. 自动化链路真实水位

### 5.1 端到端骨架（存在且在跑）

当前可见进程包括：

- `run_live_service.py`（长驻）  
- `text_watch_daemon --run-chains`（长驻）  
- `wechat_ops_agent run-daemon`  

架构上具备：微信 → 分类/抽取 → 候选/匹配 → 95306 → 入库 → Excel/上传 的自动路径。  
**成功样例**（你提供）：2026-07-15 21:00 中唐宝丽 lot2 51 车完整自动——说明主链 **能** 绿。

### 5.2 按你尺子的水位估计

| 项目 | 你自评 | 本评审观察 | 说明 |
| --- | ---: | --- | --- |
| 朝钢 | 96% | **约 85%–90%** | 同质单 lot 友好；双候选/串旧趟/上传仍出单 |
| 中唐 | 90% | **约 75%–85%** | 多 lot + 货运字段 + 半窗是主痛；7 月工单密度最高之一 |
| 吉林 | 90% | **约 75%–85%** | 马兰希望 lot5 超发 + lot6 空置为活证据 |
| 九三 | 75% | **约 60%–70%** | 多 loading 路由、完成闸污染、循环/台账类仍新；三天未手核 = 风险敞口 |

### 5.3 「未自动化」的技术本质（不是玄学）

1. **规则多入口、单点修补**（priority、匹配、货运补全）  
2. **字段历史双轨**（`plan_id` vs `order_identifier` 等）  
3. **满量/切换 lot 策略未强制**（计划箱/吨用尽后仍灌旧 lot）  
4. **OCR/JSON 语义到业务对象的解释层脆**（实装 vs 排车）  
5. **失败可见性不足**：歧义有时记「任务成功」不重试（lot4 货运工单根因 #3）  
6. **工单治理弱**：不归档、状态不统一 → 无法用看板管理风险

## 6. 测试完备性

### 6.1 现状

- 全量：`564 passed, 1 failed`（约 23s）  
- 失败例：`tests/functional/test_inbox_retry_and_cross_month_keys.py::test_lifecycle_closeout_advances_when_all_wagons_delivered`  
- 与优先级相关：`test_infer_candidate_context.py`、`test_match_release_batch.py` 有 `explicit_priority` 单测（**事后补上**）  

### 6.2 缺口（相对你的达标定义）

| 需要的测试类型 | 现状 | 风险 |
| --- | --- | --- |
| **同一规则 × 全部入口** 矩阵（match / infer / text trigger / synthesize） | 分散补测 | 打地鼠 |
| 货运补全：`plan_id`/`order_identifier` 混存 + 多 lot 歧义后重试 | 有定向测 | 需防回归 |
| 满量切换：lot 超计划/超箱后不得再入，应落下一 lot | **未见挡住马兰希望 lot5** | 高 |
| 实装/排车 JSON 语义 → 入库车数 | 多工单仍开 | 高 |
| 看板数字 = 库聚合契约 | 弱 | 中（本次 lot5 是库错不是板错） |
| 九三多 loading 禁止默认船 | 7/18 才修 | 需回归锁死 |
| 失败不得标 succeeded 且永不重试 | 工单已曝 | 中高 |

**结论**：测试对「补丁函数」较完备；对「业务不变量跨入口」不足。  
pytest 绿 **不能** 等价于你定义的自动化达标。

| 工单多 = 系统完全不可用 | **不成立**（有成功全自动日、主链在跑） |
| 工单多 = 全是未解决问题 | **不成立**（含补录、费用、当次已修） |
| 工单多 = 根因类缺陷在蒸发 | **成立**（复发主题证明） |
| 「已处理」= 自动化达标 | **不成立** |
| 你感觉没自动化 | **合理**，与证据一致 |
