# 工单:费用合同结构层与确认重量落库

- 类型: 功能实现
- 发现日期: 2026-07-02
- 状态: 已处理
- 严重度: 高

## 背景

在继续推进九三大豆 `和谐1` 费用系统时,现有结构暴露出三个基础缺口:

1. `wagon_container_shipments` 缺少显式 `freight_fee / loading_line / detail_json`
   - 导致集装箱费用仍倾向跨库回查 95306
   - 不符合“本地业务事实库优先”的目标

2. 合同条款尚未按 `route / fee item` 结构化落库
   - `contracts` 只有粗粒度主合同
   - 不能表达 route A/B/C、国铁费/地铁费/倒运费/收入等逐项条款

3. 收入侧业务确认重量缺独立落点
   - 用户给出的港口过磅/收入确认重量不能用公式推导替代
   - 需要与票面标载、推算重量分层存储

## 本工单范围

1. 给 `wagon_container_shipments` 补关键票面/作业字段:
   - `freight_fee`
   - `detail_json`
   - `loading_line`
2. 新增合同费目结构表:
   - `contract_fee_terms`
   - `contract_line_rates`
3. 新增业务确认重量表:
   - `shipment_weight_confirmation`
4. 接入 `open_db()` 主迁移入口,保证新旧库都会自动具备这些结构
5. 增加迁移 SQL 与守门测试

## 设计结论

### 一、本地费用核对主事实库

运行时费用生成/核对应优先基于:

- `wagon_shipments`
- `wagon_container_shipments`

95306 的角色是“上游同步源/补录权威”,而非日常费用计算的主查询入口。

### 二、合同结构层

#### `contract_fee_terms`

每条记录表达一个“合同中的一个费目条款”:

- `contract_ref`
- `project_id`
- `route_code`
- `fee_code`
- `pricing_basis`
- `pricing_unit`
- `default_rate`
- `counterparty / settle_party`
- `evidence_path / evidence_locator`

#### `contract_line_rates`

用于地铁费等“同一费目但按道线不同价格”的场景:

- `line_name` 如 `七道 / 八道 / 煤五`
- `rate`
- `pricing_unit`
- 与 `contract_fee_terms` / `fee_code` 关联

### 三、业务确认重量

`shipment_weight_confirmation` 用于落:

- 集装箱装箱过磅重量
- 散粮装车过磅重量
- 收入结算确认重量

其口径与票面标载、推算装载重量严格分层,禁止相互覆盖。
