# 工单:检装车文本触发器误复用旧 matched 候选

- **类型**:流程闸口缺陷
- **发现日期**:2026-06-30
- **发现来源**:朝钢马兰幸福 2026-06-30 06:51 文本触发器卡住
- **状态**:已处理
- **处理顺序**:2
- **严重度**:高 —— 文本触发器可能把当天新发车误判为旧检装车通知单已处理,导致新车列不入库、不出发运 Excel、不上传收货人系统

## 现象

2026-06-30 06:51 铁晟业务工作群消息:

```text
煤五53节朝阳西铁  马兰幸福
```

被路由为 `chaoyang_steel / inspection_text_trigger_flow / inspection_text_trigger`。

任务 `inspection_text_trigger:马兰幸福` 输出:

```json
{
  "stage": "already_handled_by_notice_chain",
  "expected_count": 53,
  "matched_candidate": "e0d89227769d4bcf7d65c268d0863b8de8dcb016"
}
```

但 `e0d892...` 是 2026-06-28 的马兰幸福 55 车候选,不是 2026-06-30 早上这 53 车。

95306 同期实际已有 2026-06-30 05:12:25~05:15:50 高桥镇 -> 朝阳西 53 车,且 `raw_core_json.tyrjzsx` 均含 `马兰幸福` 船名锚。

## 根因

`_execute_inspection_text_trigger()` 在找不到活跃候选时,会检查同船、近窗口、车数容差内的 `matched` 候选,并直接返回 `already_handled_by_notice_chain`。

当前判断缺少足够的发车事件边界:

- 没有按 `destination` 过滤 matched 候选。
- 没有按本次触发文本的 `received_datetime` / 95306 制票窗口过滤。
- 车数容差允许 53 命中旧 55。
- 旧候选仍在最大年龄窗口内,因此被误认为“通知单图已处理过”。

## 期望设计

- `already_handled_by_notice_chain` 只能命中同一发车事件,不能只靠船名和车数容差。
- matched 候选检查至少应加入:
  - destination 一致;
  - 候选/车列对应的 `ticketed_at` 与文本触发时间处于同一合理窗口;
  - 或候选 `source_image_path/message_id` 与触发文本存在明确 rendezvous 关系。
- 若没有同事件候选,朝钢文本触发器应按既有 95306 合成路径继续,不能被旧 matched 候选短路。

## 验收标准

- 构造同一船 2 天内连续发车:旧候选 `matched` 55 车,新文本触发 53 车。
- 新文本触发不能返回旧候选 `already_handled_by_notice_chain`。
- 当 95306 已有新窗口 53 车且船名锚匹配时,应合成新候选并进入标准入库/Excel/上传链路。
- 保留原有能力:真正同一事件中图片链已处理完成后,文本触发器仍应优雅跳过,避免重复发送。

- 保留同一发车事件窗口内的 matched 跳过能力:只有 `candidate.created_at` 落在文本触发时间的事件窗口内,才认为通知单图已处理完成。
