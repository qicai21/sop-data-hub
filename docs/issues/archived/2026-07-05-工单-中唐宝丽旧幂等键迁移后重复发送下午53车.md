# 工单:中唐宝丽旧幂等键迁移后重复发送下午 53 车

- 日期:2026-07-05
- 项目:中唐特钢
- 船名:宝丽
- 类型:缺陷修复 / 幂等迁移兼容
- 状态:已修复

## 背景

2026-07-05 09:16 左右,系统向数据单发群再次发送:

```text
发运数据 宝丽 共53车(按批次分块,1船)
```

该记录实际对应 2026-07-04 下午 15:40 左右已发送过的宝丽 53 车。晚间 22 点左右另有一列 53 车,那列不是本次重复发送对象。

## 已核实事实

- 本次重复发送日志:
  - `external_action_log.id=111`
  - `workflow_task_id=541`
  - `message_id=wx_2026-07_359`
  - `candidate_id=2b98be16d13f83bb61edbedbea32bd17b10e70c9`
- 该消息为 2026-07-04 15:39:47 铁晟业务工作群图片。
- 昨天下午已发送记录:
  - `external_action_log.id=108`
  - `message_id=wx_2026-07_19`
  - 旧幂等键: `...:batches:<batch_id>:53`
- 昨晚修复宝丽 15/53 问题后,发送幂等键调整为:
  - `批次集 + 本次车号集合摘要 + 总车数`
- 由于旧已发记录没有新车号集合摘要 key,今天该重复候选使用新 key 时未命中旧记录,导致重复发送。

## 根因

发送幂等键迁移缺少兼容层。

旧记录只保存 `batch_id + 车数`;新逻辑只查新 `车号集合摘要 key`。当历史已发事件被新候选/延迟候选重新跑到发送阶段时,无法识别“同一批次、同一组车号已经发过”。

## 修复要求

1. 保留新幂等键,继续允许同一 lot 后续不同车号集合的同车数列车发送。
2. 发送前增加兼容查重:
   - 按 `wagon_shipments` 查同一 `batch_id` 下是否已有某个 `source_message_id` 的车号集合与本次完全一致；
   - 若该 `source_message_id` 已存在 executed 的 `send_shipping_excel_wechat`,则跳过发送。
3. 将当前重复候选 `2b98...` 标记为 `superseded`。
4. 增加回归测试:旧格式已发 + 同车号集合重复候选必须跳过,不同车号集合不能被误挡。
5. 修复后重启 `live-service` / `text-watch`。

## 处理记录

- 已将重复候选 `2b98be16d13f83bb61edbedbea32bd17b10e70c9` 标记为 `superseded`。
- `workflow_task_executor` 增加 `_find_sent_same_car_set_event`:
  - 从 `wagon_shipments` 按 `batch_id + source_message_id` 聚合车号集合；
  - 若某个历史 source 的车号集合与本次完全一致,且 `external_action_log` 已有 executed 的 `send_shipping_excel_wechat`,则认为该物理发运事件已发送；
  - 该检查用于兼容旧幂等键,不会挡住同一 lot 后续不同车号集合的 53 车。
- 发送逻辑在新幂等键未命中时,会继续执行同车号集合历史已发检查,命中则跳过发送。
