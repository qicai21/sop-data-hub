# 工单：顺序放货项目自动生成唯一lot匹配优先级

- 日期：2026-07-25
- 状态：已完成
- 范围：中唐特钢、朝阳钢铁、吉林金钢

## 背景

`BusinessDataAgent.upsert_release_dispatch_match_rule()` 当前将所有
`release_dispatch_match_rules.priority` 固定写为100。同船存在多个开放lot时，
候选无法按既定发运顺序匹配；规则刷新还会覆盖人工校正，导致宝丽连续两次出现
检装车候选挂起。

九三大豆的lot通常区分集装箱与散粮车，是并行运输类型，不能直接套用lot编号顺序。

## 修复要求

1. 项目SOP显式声明是否采用顺序lot匹配。
2. 中唐、朝钢、吉林金钢按lot编号生成稳定唯一优先级：
   `lot01=100`、`lot02=200`，依次递增，数字越小越优先。
3. `all_loaded`及后续终态规则仍退出active池，不参与后续匹配。
4. 九三大豆不启用顺序lot优先级，避免集装箱和散粮车相互抢批次。
5. 非顺序项目已有人工优先级在刷新规则时不得被默认值100覆盖。
6. 增加回归测试，刷新现有规则并验证宝丽lot5优先于lot6。
7. 提交git，重启相关服务并核验。

## 处理结果

1. 在中唐、朝钢、吉林金钢项目SOP中启用
   `sequential_lot_match_priority`；九三大豆未启用。
2. 新增统一优先级生成逻辑，按lot序号生成稳定优先级。规则刷新时：
   - 顺序项目自动校正为lot对应优先级；
   - 非顺序项目保留已有人工优先级，不再重置为100。
3. 已备份数据库：
   `data/backups/sop_agent_20260725_before_sequential_priority_refresh_0625.sqlite3`。
4. 已刷新现有匹配规则。当前宝丽：
   - lot05：priority=500，active；
   - lot06：priority=600，active。
5. 实际匹配验证：宝丽无lot货运上下文明确匹配lot05，
   原因为`explicit_priority`，不再因两个开放lot同优先级而挂起。
6. 九三大豆勇气lot01（集装箱）和lot02（散粮车）均保持priority=100，
   不会被顺序项目规则错误串行化。
7. 相关回归测试通过：`16 passed`。
8. 已重启并确认运行：
   - `com.qicai21.sop-data-hub.live-service`
   - `com.qicai21.sop-data-hub.text-watch`
