# 工单:中唐货运消息「识别了却填不进批次」——匹配挂起后不重试

- **提出日期**:2026-06-27
- **类型**:功能缺陷(匹配时序 + 无重试)
- **状态**:即时数据已修复;系统性重试机制待排期
- **提出场景**:用户反映"中唐特钢发运群的货运消息始终不能自动识别",怀疑 yaml 缺规则。

---

## 一、现象 vs 真相

**现象**:中唐发运群发的结构化货运消息(供方/船名/货名/港口/数量/计划号/合同号)看上去"没被识别"——对应批次的计划号一直空着。

**实测样本**(wx_2026-06_46,2026-06-26 11:35):
```
供方: 福建漳龙集团有限公司（浩宇纵横）   船名:丰收散运   货名:纽曼粉
港口:锦州港   数量:12177   计划号:90260600088   合同号:ZLZT-2026062401
```

**真相**:**规则在、识别也对,卡在匹配后不重试。**
- ✅ yaml **有规则**:`listening_tasks` 含 `match_text_template` + `freight_detail_flow` + 进口/到港船名核对规则。
- ✅ 35B **抽取正确**:船名/计划号/合同号/数量全抽对(task #416 succeeded)。
- ❌ **匹配挂起**:#416 内部结果 `suspended`,理由"货运船名丰收散运对不上任何在途中唐到港船 → 疑似进口大船/转水"。但 lot08(丰收散运)此刻是 `pending_freight` 且缺计划号,**本该按规则1命中**。推断 11:35 处理瞬间 lot08 还不在可匹配状态(`enrich_release_batch._OPEN_FREIGHT_STATES`),**走了规则2挂起;而挂起后系统永不重新匹配** → 计划号永久空着。

## 二、即时修复(已做)

重跑 `auto_enrich_release_batches_from_zhongtang_supplement(candidate, apply=True)` →
lot08 立即填上 `合同=ZLZT-2026062401 / 计划号=90260600088`。**证明规则本身没问题,缺的是重试。**

## 三、根因 + 系统性分析(同类反复问题)

**本质 = 「依赖项 later 才就绪时,挂起态不会自愈重匹配」。** 这是一个**反复出现的同构缺陷**,本仓已多处踩到:

| 处 | 依赖项 | 早到时的表现 | 现状 |
|---|---|---|---|
| 中唐货运消息 → 填批次计划号 | 对应 release_batch 变 pending_freight | suspended,永不重试 | **本工单** |
| 检装车文本触发 → rendezvous 95306 候选 | 95306 制票 | 有 grace + 超时告警 | 已有部分重试([[inspection_text_trigger_arch]]) |
| 出港计划 → 建批次 | (无依赖,但)VL 误读/过滤致 ingested=0 | 静默 0 批次,无告警 | 见 `2026-06-27` 出港0批次盲区 |
| waiting_media(图片) → 抽取 | 图片下载完成 | 有 retry index + max_retries | 已有重试 |

**规律**:凡是"A 依赖 B,B 可能晚于 A 就绪"的环节,都需要**重试/rendezvous**;缺了就表现为"功能时灵时不灵、看起来没识别"。检装车/waiting_media 已补,**中唐货运 + 出港0批次这两处还是裸的**。
