## 3. 根因分析(数据侧观察)

链失败 `candidate missing fields: ship/dest/project 全空`,叠加三个缺陷:

1. **多船混合检装车单未拆分**:一张图含 3 组(中联发→朝阳西、亚历山大→凌源东、宇凡26→赤峰南),只有中联发是朝钢。链没有按 ship/到站把本项目组(中联发→朝阳西)分出来,候选 ship/dest 取不到 → 空。
   - 关联既有工作:#130 复合检车单多组拆分([[inspection_payload_multi_group_split]])、#145 残留"纯图片多船 LIMIT 1"([[inspection_text_trigger_arch]])。本例就是 #145 残留的真实暴露。

2. **车号 OCR 失败未兜底**:`car_nos=['2026618']`(日期误读成车号),`rows_count=3`(只抽到3行汇总)。朝钢真权威车号在 95306(44车已齐),链应在图车号不可用时**回退以 95306 为权威**,而不是依赖图。

3. **无法 infer 时硬 fail,而非挂起**:候选 ship/dest/project 空时,按业务铁律应 **挂起 `pending_review` + infer 三层级联兜底**([[inspection-candidate-no-ship-suspend-rule]]),并可从已成功的发车触发器(#360 中联发/朝阳西/44车)会合补字段。实际却 raise "candidate missing fields" 直接失败、候选不落库。触发器与候选的 rendezvous 没生效。

## 4. 期望行为(给代码会话)

- 多船混合检装车单 → 按 (船名, 到站) 拆成 N 组;**只保留有 yaml 的跟踪项目组**(中联发→朝阳西=朝钢),非跟踪组(亚历山大/宇凡26)透明丢弃([[tracked-projects-yaml-only]])。

## 7. 处理进展(系统开发会话,2026-06-19)

### 先纠 issue 一处误判
候选 `db67ef…` **其实已落库**(查到了:`ship='' dest='' project='' candidate_status='pending_review' wagon_count=3`)——infer 三层那层做对了、按 no-ship 铁律挂了 pending_review。**不是"候选不落库",而是链执行器在其后又硬 fail 了一道。**

### ✅ Fix A(已做 + 测试):链不再硬失败 → 优雅挂起
`workflow_task_executor.py` `_execute_chaoyang_inspection_chain` 第 863 行:ship/dest/project 缺失旧逻辑 `return failed`(污染 task 状态、inbox 显示 task_failed、像系统崩)。改为**挂 pending_review + 返回 skipped**(镜像正下方 907-913 match 失败的正确姿势),候选保留给人工/后续 infer 接管。守门测试 `tests/functional/test_inspection_chain_suspend_not_fail.py`(2 例)+ fanout 回归 3 例全绿。

### ⏳ 待用户拍板(B / C,涉及启发式与对外动作,不盲改)

### ✅ Fix B(已做 + 测试):检装车通知单 标题硬锚闸(掉了的那道闸补回)
**真根因(用户细挖方向命中)**:live 分类器 = sop-data-hub `classifier/classifier.py`(`BusinessGroupImageClassifier.classify`,runner.py 调用)。它对 `手写箱号车号表` 有 `detected_title` 安全闸,**但对 `检装车通知单` 没有任何 title 校验**;prompt 又有"60% 视觉证据即输出"的鼓励语 → VLM 看见同版式印刷表(日现场工作记录表:到站/船名/品名/道线/车数列)按版式判成检装车单,无人拦。wx-ops-agent 里那套**严格 title 锚定**的 prompt(`scripts/classify_manual_document_types.py`:"标题明确含'检、装车通知单'" + 专门"日现场工作记录表→other"卡)只在 batch 脚本,**没接进 live**;live 的 `thumbnail_sentinel.py` 只是 4 类粗筛(检车单按版式、无 title、无日报类)。
**修复**:① `classifier.py` 加确定性 title 闸——category=检装车通知单 但 `detected_title` 归一(去顿号/空格)后不含"检装车通知单" → 降级 `other`,不进抽取链;② `prompts.py` 加反向铁律——"无该标题字样即使版式像检车单也绝不判检装车单"。守门测试 `tests/test_classifier_title_gate.py`(4 例:无标题降级/真标题保留/顿号归一/他类不受影响)+ image_ingestion_contract 回归全绿。live-service 已重启。

### ✅ Fix C(已做 + 测试):无检装车通知单 → 从 95306 合成候选自动闭环(到 match,不上传)
发车文本触发器(`_execute_inspection_text_trigger`)在等满**宽限期 3h** 仍无候选时,**朝钢专属**靠 95306 托运人记事 `tyrjzsx` 船锚(见 [[95306-tyrjzsx-ship-anchor]])从 95306 反查权威车合成候选,委托既有检验链跑到 ingest/match。实测 tyrjzsx 锚 100% 命中(2026-06-19 朝阳西铁矿窗口正好 44 车、全中联发)。
- 新模块 `src/sop_hub/sop/inspection_95306_synthesize.py`(按 dest+cargo+tyrjzsx含船名+触发时间窗反查,车数与预期差>4 不合成)。
- 链加 `skip_upload` 参数:合成候选**不自动上传鞍钢**(对外动作),发群提醒"已 ingest/match,待人工核对后再走标准上传+反查"。真通知单先到则仍走原 rendezvous(正常自动上传)。
- 宽限期(3h)内仍 pending 给真通知单机会;合成失败(95306 没车/车数不符)落回原超时逻辑。
- 测试 `tests/functional/test_inspection_95306_synthesize.py`(4 例:命中合成/无车/车数不符/tyrjzsx滤别船)+ inspection 链全套 24 例 + 广回归 48 例全绿。text-watch 已重启。
