- **提出场景**:循环列项目(九三大豆 和谐1:集装箱 + 散粮)每日晨报盘点,现有数据散在 `container_pool_snapshot` / `wagon_body_pool` 两表,缺一个**直观体现箱子转一圈、且能今昨对比**的看板。
- **类型**:功能开发(非缺陷)

## 一、目标(用户三条原始诉求)

1. **箱子池状况** = 当前存量 + **昨日对比变化**(每节点带 `+进/-出`)。
2. **循环列行进情况**:4 列车体顺时针错开转圈,看板要看得出每列当前在哪一段。
3. **直观**:用流水线 + 节点 `当前数(+昨进/-昨出)` + `#列号` 的记法。

## 二、样式①（定稿）—— 箱循环流水线(矩形闭环)

> 下图为**测试展示数据**,数字仅示意走向与排版,实装时全部由台账/ingest 自动填。

```
和谐1 箱循环   06-19 早7点          池 588(重298 | 空290)   守恒 ✓


  港空 52   ──▶   港重 100   ──▶   途重 100   ──▶   新台子 98
 (+100/-110)     (+110/-100)        (#2)              │
                 #4 装·pm发                           │
                                                      ▼
      ▲                                          三三0总 138
      │                                          (+100/-98)
      │                                          2号列 卸重装空
      │                                              │
      └──────────────  返空 98 (#1)  ◀────────────────┘
```

### 节点定义与排版约定

- **闭环走向**:顺时针。顶行去程(左→右)`港空 → 港重 → 途重 → 新台子`;右侧竖线下落到 `三三0总`;底行返程(右→左)`三三0总 → 返空 → 港空`。
- **6 个节点**:
  | 看板节点 | 含义 | 底层字段(`container_pool_snapshot`) |
  |---|---|---|
  | 港空 | 港内可用空箱 | `port_empty` |
  | 港重 | 港内待发重箱(=当前在装那列) | `port_loaded` |
  | 途重 | 在途去程重箱 | `transit_loaded` |
  | 新台子 | 新台子站线上(过路位) | `line330_loaded`（线上重，本项目当前口径）|
  | 三三0总 | 国储库三三0处 **重+空合计** | `ground330_loaded + ground330_empty` |
  | 返空 | 反空在途空箱 | `transit_empty` |

- **`(+进/-出)` 只标"会变箱态"的节点** —— 港空 / 港重 / 三三0总。途重、新台子是**过路位**(箱子只路过不变态),**不标 `+/-`**。
  - 港空:`+返空到港 / -装车`
  - 港重:`+装车 / -发车`
  - 三三0总:`+到达 / -返空发出`（三三0 的 `-出` 应 = 返空节点的箱数,首尾咬合自洽)

- **循环列(#列号)**:每个**在循环中的列**挂 `#n`(n=home_cycle_no)。4 列各就各位:
  - **港重 = #当前装列**,额外标 `装·pm发`(在装车 = 港重节点本身,不另起节点;装完发车后 `#n` 标记右滑到途重)。
  - 途重 = `#在途列`、三三0 = `#正在卸装的列`、返空 = `#返程列`。
  - **港空不挂列号**(它是喂给在装列的空箱池)。
  - 可选:在装列标进度 `装 100/110`(已装/计划),看装车快慢。

- **「在装车」的表示**(用户明确要点):**就是港重节点 + `#n 装·pm发` 标记**,因为"港内在装"的箱子物理上就是港重那一堆,归属当前装的那列。发车后标记随箱右移到途重。

- **三三0总的动态**:除 `(+进/-出)` 外,补一行**当前作业列状态**(如 `2号列 卸重装空`),把"哪列正在三三0卸重装空"标清楚。

- **顶部标题栏**:`船名 箱循环 + 日期时刻 + 池总(重|空) + 守恒✓/⚠`。守恒由 `container_pool_snapshot --check` 结果驱动(✓ 或亮异常)。

- **排版**:节点间留足横向间距、闭环上下留纵向空行(用户要"更清晰")。

## 三、`+进/-出` 增量算法(关键)

每个节点的昨日 `+进/-出`,优先级数据源:

1. **95306 状态流转计数**(`wagon_container_shipments`,按日 group):
   - 昨日 `已发车` 箱数 → 港重 `-出` / 途重 `+进`
   - 昨日 `已到达` 箱数 → 途重 `-出` / 三三0(或新台子)`+进`
   - 昨日 `货物已交付` → 三三0 内部重→空转化
2. **快照今昨差**:`container_pool_snapshot` 今日 vs 昨日同节点字段相减,做净变化兜底/交叉校验。
3. **晨报字段**(field,部分流量 95306 不开票):**装车量、返空到港量** 当前只在晨报 markdown 里,需从 `--record` 时一并落库(建议 snapshot 表加 `daily_loaded` / `daily_returned` 等流量列,或单开一张 `pool_flow_daily`)。

> ⚠️ 实施注意:返空(`transit_empty`)、新台子/三三0 空箱这类**晨报不一定每天给数**的节点,历史上靠池守恒反推过,易偏(见 [[jiusan-pool-tracking]] 6/19 踩坑)。**有实数用实数,没有就标 `inferred` 留空,别硬反推填进 `+进/-出`**。

## 四、循环列 #列号 来源

- `wagon_body_pool`:`home_cycle_no`(列归属)、`last_seen_cycle_no`(当前编组)、`last_seen_date`。
- 列→车→箱:`wagon_container_shipments.car_no` JOIN `wagon_body_pool.car_no`。
- **4 列循环**(2026-06-19 用户现场确认,从 3 列增到 4 列):① 港装 ② 在途去程 ③ 三三0卸 ④ 返空,各 ~100 箱错开。第 4 列 = 当日港内在装那列。
- 每列「上次发锦州港时间 / 下次预计」可取 `wagon_container_shipments` 各列发车的 `ticketed_at` 时间窗(节奏约 2–3 天/趟,50车/100箱)。

## 八、BUG(2026-06-22 用户报):箱数冻结在早7点快照 ↔ #N列位置取95306实时 → 自相矛盾

**现象**:6/22 17:23 看板上 **1号列已标在"途重"位**(95306 实时:已发车=100箱/50车,1号列白天发车了),但**途重箱数显示 0**、**港重 165 没核减**。即"1号列在途"却"途重0",港重还含着发走的那 100 箱。

**根因**:箱循环图的**节点箱数取自当日早7点 `container_pool_snapshot`(冻结值)**,而 **#N号列位置取自 95306 实时状态**。早7点 1号列确实没发(快照 `transit_loaded=0`、`port_loaded=165` 对的),但白天一发车,95306 把 1号列推进到"途重位",**箱数却没跟着动** → 表头写"现状 17:23" 用的却是早上的箱数。这正是第七节"口径=全live"**设计了没落实**的点:循环箱数本应跟 95306 实时联动,实现时写死成了快照。

**期望修复**:循环列在载/在途/到站/返程的**箱数也走 95306 实时**(与 #N列位置同源),而非冻结快照:
- 途重 = 95306 `已发车` 箱数(live)
- 港重 = 快照 `port_loaded` − (自快照以来已发车增量) ← 发车要核减港重
- 新台子/三三0 = 快照底 + 95306 `已到达`/`已交付` 当日推进
- **只有 95306 给不了的纯库存(港空、330落地空)才沿用快照底**
- 验收:1号列发车后,途重立即显 100、港重核减 100,表头"现状"与箱数同一时刻一致。
- 注意第七节"固有限制"(制票滞后):刚物理装车没出票的列,95306 认不全 → 港重在装列仍靠快照兜底,这块容差保留、图例标清。

### 八.2 追查(2026-06-23):看板根本不会"随晨报自动更新"——晨报→快照这一环无任何自动化

**用户报**:6/23 晨报已进群,但看板还停在 6/22。**调查结论(全链路)**:

```
晨报进群 ──✗ 断 ──▶ [解析→写 container_pool_snapshot] ──▶ 看板实时读最新快照
                  ↑ 这一环从来不存在
```

1. **看板侧无问题**:`jiusan_cycle_board.render_lines()` 每次 `ORDER BY snapshot_date DESC` **实时**取最新快照,无缓存。显示 6/22 仅因库里最新快照=6/22。
2. **6/23 快照不存在,且无任何东西自动生成它**:全仓 grep"晨报→snapshot 自动环节"零命中;launchd 6 个 job(jiusan-sync/live-service/text-watch/email-bot/hermes)无一解析晨报;`container_pool_snapshot` 历史记录时间(8:40/10:08/11:17)全是**手动 `--record`** 痕迹。
3. **九三晨报根本没走群文本管道**:跨所有群(中唐/数据单发/铁晟…)搜 6/22–6/23 "港内/可用空箱/和谐/诚信/散粮"零命中;历史晨报均为**用户直接粘贴**给会话,不入 chat_records。6/23 数据单发群新消息是朝阳/中联发(chaoyang_50cars.xlsx),非九三晨报。
4. **唯一会自动动的**是 jiusan-sync daemon,只刷 95306 派生部分(#列位置/散粮车状态),**不碰箱数快照**。

**根因定性**:不是 daemon 挂了,而是**"晨报→看板"自动链从未建立**;箱数节点(港重/途重/港空…)永远停在最后一次**手动**快照。与 §八(箱数取冻结快照 vs 列位置取实时)是同一病根的两面。

**期望修复(二选一或叠加,请用户/开发定)**:
- **A 看板自洽兜底**(轻):render 时若最新快照 `snapshot_date < 今天`,表头明确标"⚠ 快照为 N 天前(港重/池底可能过时)",别用旧箱数冒充"现状",避免误导。
- **B 建晨报→快照自动入口**(重,根治):晨报解析器(文本/图)→ 自动 `container_pool_snapshot` record。需先定晨报载体:① 让晨报进固定群+固定格式 → text-watch/分类器解析;② 或保留手动,但提供"贴文本一键 record"工具。**晨报载体目前不固定(靠人粘贴)是上游瓶颈**,自动化前需先固化它。
- 配合 §八:箱数节点改走 95306 实时 + 快照只做纯库存底,可一并降低对"每日新快照"的依赖。
