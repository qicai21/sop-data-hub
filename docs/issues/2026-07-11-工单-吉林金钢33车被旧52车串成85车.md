# 工单: 吉林金钢 33车事件被旧 52车串成 85车

## 背景

`2026-07-11 01:53:19`，铁晟业务工作群文本：

- `煤一 33节 四平铁 马兰希望`

系统随后在 `03:53:43` 向 `数据单发群` 发送了：

- `吉林金钢发运数据 马兰希望 lot04 85车`
- 附件 `吉林金钢_发运数据_20260711_85车.xlsx`

但实际本次只发了 `33` 车。

## 根因

不是单纯 Excel 模板问题，而是 **executor_runner 事件收口口径错误**：

1. `query_95306` 在 `24h` 窗口内查到：
   - `exact_match_count = 33`
   - `ambiguous_count = 52`
   - `total_candidates = 85`
2. `create_wagon_shipments` 对这 `85` 条全部出 plan：
   - 本次 `33` 条 `insert`
   - 上一趟 `52` 条 `skip_existing`
3. `executor_runner` 旧逻辑构造 `event_wagon_ids` 时，把 `insert + skip_existing`
   全部并入本次事件，导致后续：
   - 发运 Excel 导出 `85` 车
   - 工厂上传校验报 `跨 2 趟(['wx_2026-07_849', 'wx_2026-07_871'])`
   - 但微信发表步骤仍把错表发出

核心问题是：

- **当前消息的 event 范围应优先由 `source_message_id` 锚定**
- 不能仅靠 `ydid/car_no` 从同 batch 历史中反捞

## 本次修正

修改：

- `src/sop_hub/sop/executor_runner.py`

规则调整：

1. `_fetch_event_wagon_ids()` 新增 `source_message_id`
2. 事件收口顺序改为：
   - 先按 `batch_id + source_message_id`
   - 若当前消息尚未在库中留下 `source_message_id`，再退回 `ydid`
   - 最后才退回 `car_no`
3. `run_departure_executor_chain()` 在构造 `event_wagon_ids` 时传入当前 `event.message_id`

这样即使 95306 时间窗混入上一趟旧票：

- 旧票只会在 `create_wagon_shipments` 中被识别为 `skip_existing`
- 不会再进入本次 Excel / 上传 / 发微信范围

## 回归测试

新增/更新测试：

- `tests/test_event_scoped_wagon_filters.py`

覆盖点：

1. 同一 batch 中旧/新两趟复用车号时，仍优先按 `ydid` 收口
2. 当存在 `source_message_id` 时，必须优先按当前消息收口，而不是把旧趟一并带入

## 验证

- `PYTHONPATH=src pytest -q tests/test_event_scoped_wagon_filters.py`
  - `7 passed`
- 在当前生产库实测：
  - `batch_id=lot04`
  - `source_message_id=wx_2026-07_871`
  - `_fetch_event_wagon_ids(...)` 返回 `33` 条

## 业务结果

修复后，吉林金钢这类“上一趟已入库、本趟新发车”的文本事件：

- 发运 Excel 应只覆盖当前消息对应车列
- 工厂上传仍保持 per-event 校验
- 不会再出现 `33车 -> 发85车表` 的串趟问题
