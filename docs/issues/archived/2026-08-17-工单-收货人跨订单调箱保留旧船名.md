# 工单：收货人跨订单调箱保留旧船名

- **日期**：2026-08-17
- **状态**：已完成
- **范围**：吉林金钢 / 收货人系统 / `factory_edit.move_factory_records`

## 现象

2026-08-16 海洋征服者与富翔7的 32 车混列人工更正后，收货人门户中：

- 海洋征服者 lot12 订单的 50 箱中，6 箱 `boatName=富翔7`；
- 富翔7 lot03 订单的 14 箱中，6 箱 `boatName=海洋征服者`。

订单号、货名和合同号正确，船名是跨订单移动前的旧值。

## 根因

`move_factory_records` 只将门户原始 payload 的 `orderId` 替换成新订单号。
门户会按新订单自动归一合同号，但不会归一 `boatName`；旧验证又只检查
记录从旧订单消失、在新订单唯一出现，未检查目标业务字段。

## 修复

1. `FactoryEditTarget` 支持每条目标记录的白名单字段更新。
2. 跨订单移动时将 `orderId` 与 `boatName` 一次提交。
3. dry-run、断点重跑与 postflight 都验证目标字段。

## 验收

- 本次 12 箱逐条修正，两订单船名各自 100% 正确，无重复。
- 本地 64 个 `portal_id` 与门户反查集合一致。
- 单元测试覆盖目标船名更新和已移单但字段未更新的恢复。

## 处理结果

- 海洋征服者 `CGR20260814093728`：本次 50 箱 `boatName`全部为海洋征服者。
- 富翔7 `CGR20260812140810`：本次 14 箱 `boatName`全部为富翔7。
- 12 箱船名逐条更新并反查通过；无重复，64 个门户 ID 与本地一致。
- 证据：`runtime/factory_edit_audit/20260817_jg_32car_boat_name_fix_plan.json`、
  `runtime/factory_edit_audit/20260817_jg_32car_boat_name_fix_result.json`。
- `move_factory_records` 已支持并验证目标业务字段，包括断点后订单已移但船名
  未更新的恢复路径。
- `make test`：698 通过；`make smoke-runtime`：通过。
