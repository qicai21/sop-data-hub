# 工单：检装车分类命中后提取器二次拒绝导致62车静默挂起

- 日期：2026-07-24
- 项目：中唐特钢
- 状态：处理中
- 来源消息：`wx_2026-07_2018`、`wx_2026-07_2019`

## 现象

2026-07-24 14:33:59，铁晟业务工作群发送宝丽62车检装车通知单；14:34:13
发送文本：

`煤四，汐子铁，宝丽，62节`

图片分类阶段已判定为“检装车通知单”，但 `InspectionSlipEngine` 的入口版式判断
再次返回 `is_inspection=false`，最终提取 JSON 为：

- `doc_type=unknown`
- `rows_count=0`
- `is_target=false`

因此没有建立 `inspection_ingestion_candidates`。文本任务 `762` 虽已创建，却只能
在 `waiting_inspection_notice` 内部重试；当前看板既没有候选挂起，也没有发运
Excel。检查时95306尚未出现本列制票记录。

继续检查发现，代码声明由 `pending_match_verifier` 延迟重试
`pending_95306_match`，但该验证器未接入任何常驻服务；即使候选建立，后续制票
也不会自动推动。

## 根因

分类器已经通过标题硬锚确认图片属于检装车通知单，但提取器仍执行一套独立的
VLM文档类型判断。第二次概率判断可以否决前一层确定性分类，导致同一张图片出现
“分类命中、提取拒绝”的矛盾状态。

## 修复要求

1. 分类器已确定为“检装车通知单”后，提取器不得再因入口VLM判断失败而直接退出；
   应继续页头和表格明细提取。
2. 保留独立调用提取器时的文档类型保护，不能放宽非目标图片。
3. 增加稳定测试，覆盖“可信分类命中 + 入口VLM误判 false”仍继续提取。
4. 恢复本次62车候选，车号以原图序号1-62为准，项目中唐特钢、船名宝丽、
   到站汐子、作业线路煤四。
5. 95306未制票时保持可见挂起；制票后由标准链生成Excel并发送。
6. 将候选延迟验证器接入启用外部链的 `text-watch`，按受控周期重试。
7. 修改后提交git并重启加载相关代码的服务。

## 验收标准

- 本图生成62行有效车号候选，不重复、不漏行。
- 文本任务能与候选汇合，不再停留于“未等到通知单”。
- 未制票时明确显示挂起原因；制票后标准链可继续。
- 回归测试通过，服务加载新代码。

## 处理结果

- 原图重新提取出62行，序号1–62连续，62个车号均为唯一7位数字；页头煤四，
  页脚装车62、排车0。
- 已建立候选 `85718ace559d437d1447d2150d643a05864cf0eb`：
  - 中唐特钢 / 宝丽 / 汐子 / 62车；
  - 关联宝丽 lot5；
  - 当前 `pending_95306_match`；
  - 原因：通知单前4个装车号在95306均未制票。
- 货运看板已显示“挂起运单 1”，不再静默。
- 分类器可信命中后，提取器不再用入口VLM概率判断直接否决；直接调用提取器时
  原文档类型保护仍保留。
- `pending_match_verifier` 已接入启用 `--run-chains` 的 `text-watch`，
  每60秒至多重试一次；服务重启后候选更新时间已自动推进，证明调度生效。
- `live-service`、`text-watch` 已重启并持续运行。
- 相关测试合计 `48 passed`。

## 后续发现：延迟重试丢失既有批次归属

延迟验证器启用后发现两条不应长期挂起的数据：

1. 宝丽62车候选在建立时已经关联 lot5；之后宝丽 lot6 新建。延迟重试执行器没有
   保留候选已有且仍有效的 `release_batch_id`，重新匹配时看到两个开放批次，
   将候选改成 `pending_review / multiple_candidates`。
2. 环球信任35车候选中的33个实装车号已经全部落入环球信任 lot8，且 lot8 已
   `confirmed_received`；验证器仍先查“开放批次”，得到 `no_open_batch`，
   使已完成历史候选重新出现在看板。

补充修复要求：

- 候选已有批次仍为开放状态，且项目、船名、到站一致时，延迟重试保持原归属；
  不因后来新建批次而重新歧义。
- 候选全部实装车号已经落入其关联批次时，直接将候选收口为 `matched`，不再要求
  存在开放批次。
- 宝丽62车保持归属 lot5；环球信任历史候选归档收口。
