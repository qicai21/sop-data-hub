# 工单:检装车通知单车号 vs 95306 自动核对纠错

- 日期:2026-06-29
- 分支:main(单分支)
- 关联记忆:`95306-window-reconcile-rule`、`inspection_text_trigger_arch`、`inspection_candidate_no_ship_suspend_rule`
- 状态:已实现 + 已测,**未部署**(待用户过设计 + diff,再由主机重启 daemon)

## 一、现象

检装车候选在 95306 时间窗反推后停在 `pending_review` 等人工,本可自动更正后继续。

真实案例(2026-06-29 丰收散运 55 车):
- 2 个"真排车" **1848879、1731344** 其实是**通知单录错的车号**(不是 OCR,是单子本身写错)。
- 它们对应 95306 窗内的真号 **1846879、1721344**(各差 1 位)。
- 因为差这 2 个,反推出现"真排车数 == 异常数 == 2",分类逻辑判 `anomaly` → 候选挂 `pending_review`,需人工裁决。

## 二、根因(只读定位)

链路:`text-watch` / `rail95306-sync` daemon → `workflow_task_executor._execute_chaoyang_inspection_chain`(检装车链)→ `inspection_window_recover.recover_loading_cars_via_window`(95306 时间窗反推)。

- 反推函数 `src/sop_hub/sop/inspection_window_recover.py`:
  - 找锚点 → 建 ±window 分钟时间窗 → 拉窗内同到站+货名的制票车号集 `window_cars`。
  - 集合运算(原 L142–144):
    - `loading = window_cars ∩ notice_set` —— 真装车权威列表
    - `missing_from_notice = window_cars − notice_set` —— **异常**(窗内有、通知单没)
    - `notice_only = notice_set − window_cars` —— **真排车**(通知单有、窗内没)
  - 原 L153–157:只要 `missing_from_notice` 非空,就 `status = "anomaly"`。
- 触发 `pending_review`:`src/sop_hub/sop/workflow_task_executor.py` 原 L1276–1295,`recover["status"] == "anomaly"` 分支把候选置 `candidate_status='pending_review'`。
- 候选车号存放:`inspection_ingestion_candidates.car_numbers_json` / `payload_json`(`src/sop_hub/data_agent/db.py` L172–173)。
- 入链前校验:release_batch 匹配(`match_release_batch_*`,多义/无批挂 pending_review)→ `no_ticket_yet` 挂 `pending_95306_match` → 本工单的 `anomaly` 挂 `pending_review` → footer 装车数 sanity → 全车落库 guard。

根因:通知单录错车号这一类 `anomaly`,与"拼批/窗太宽"的 `anomaly` 被一视同仁,缺一个"错号 ↔ 真号高置信配对自动更正"的中间档,导致本可自动更正的候选被挂人工。

## 三、设计与保守边界

在反推函数算完三类集合后,新增"自动核对纠错"step(`_autocorrect_notice_car_numbers`):

触发条件(全部满足才尝试):
1. 开关开启(`auto_correct_car_no`,默认开)。
2. **真排车数 == 异常数 == N**,且 **1 ≤ N ≤ max_correct_pairs**(默认 3)。

配对依据(`_similar_car_no`,稳健取法):
- 两个车号必须**全数字、同长度**。
- **相邻两位转位**(如 1721344↔1271344)→ 记 `transposition`,距离 1。
- 否则按 **Levenshtein 编辑距离 ≤ 阈值**(`max_correct_edit_distance`,默认 2)→ 记 `substitution`。

唯一性(保守边界,任一不满足就**整体放弃、维持原 `anomaly`/`pending_review`**):
- 每个真排车在阈值内必须**恰好唯一**配到一个异常车(0 个或 ≥2 个 → 放弃)。
- 配对必须**单射**(两个真排车不能配到同一异常车 → 放弃)。
- 真排车数 ≠ 异常数 → 放弃;近似度低于阈值 → 放弃;N 超 `max_correct_pairs` → 放弃。
- 一句话:**拿不准就挂人工,绝不乱配。**

纠错成功后:
- 把配对的异常车并入真装车权威列表 `loading`;从 `missing_from_notice` / `notice_only` 剔除。
- `missing_from_notice` 清空 → `status` 回到 `ok`,候选随之干净匹配、照常推进(不再 `pending_review`)。
- 返回新增字段:`corrections`(旧号→新号 + 距离/依据 + `source=95306_window`)、`auto_corrected`(bool)。

审计(`persist_car_no_corrections`,由 executor 在 `ok` 路径调用):
- 写表 `inspection_car_no_corrections`:旧号、新号、编辑距离、配对依据、`source=95306_window`、锚点车/锚点制票时间/窗口分钟、时间戳。
- 把候选 `car_numbers_json` 里的错号替换为真号。
- **幂等**:同 `(candidate_id, notice_car_no, window_car_no)` 已存在则跳过,避免 `rail95306-sync` 延迟验证器重试时重复落审计。

可配置(便于关停):`autocorrect_config_from_env()` 读环境变量,executor 透传——
- `INSPECTION_AUTOCORRECT_CAR_NO`(默认 `1`;设 `0`/`false`/`off` 关停)
- `INSPECTION_CAR_NO_MAX_EDIT_DIST`(默认 `2`)
- `INSPECTION_CAR_NO_MAX_PAIRS`(默认 `3`)

不变量:窗口干净(无异常)时 `corrections=[]`、行为与改前完全一致(#144 等回归不受影响)。
