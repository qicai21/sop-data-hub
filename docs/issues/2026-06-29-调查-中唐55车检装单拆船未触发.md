### 没触发的根因(定位到具体数据状态)
本单两个船名扫描时:
- seq3 `丰收散运` → 命中 **active** rule `8b6fa8eb…`(批次 `c49a7b5f…`,`dispatch_status=loading`)→ **记锚点 ✓**
- seq8 `环球信任` → **无任何 active rule 命中 → 不记锚点 ✗**

`环球信任` 的全部 rule 状态:

| rule | batch | status |
|---|---|---|
| e9ea578b / 0882bd3a / 1fb30311 / 535db725 / db57566b | 6 月初的 5 个旧批次 | **completed**(2026-06-08 收妥) |
| **(无 rule 行)** | **`bb15b6b0…`(2026-06-27 新建,`dispatch_status=pending_freight`)** | **根本没有 rule 行** |

→ 只有 1 个锚点(丰收散运)。锚点前向吸收把 seq1–2 的段头也并进丰收段,`prefix_end=0` 无前缀段,`segments` 收敛成 1 段 → **`return [payload]` 不拆** → 整 55 车走单候选,`ship_name` 经 `infer_candidate_context` 落到唯一命中的 active 批次「丰收散运」。

### 三选一定性
- **不是**解析层漏抽第二船名(两船名+两节数都在 payload ✓)。
- **不是**中唐没接拆分(拆分逻辑对所有项目通用,无 project 闸;若两船都有 active rule 就会拆)。
- **是**「拆分条件」没命中:**第二船「环球信任」当前在途批次 `bb15b6b0`(pending_freight)缺一条 active match rule** —— 按 `refresh_release_dispatch_match_rules()`(agent.py L904-906)`pending_freight` 本应映射成 `active`,但这条 rule **从未被生成**(批次卡在 pending_freight 未推进,关联既有记忆「中唐货运消息匹配挂起不重试 / pending_freight 批次未自动推进致检装车候选挂起」)。**单船锚点 → 拆分天然不触发。**

附带的隐患(非本次根因,但加剧静默):L1155 在只有 1 锚点时直接整单返回,**没有"单子里明明有第二个船名 token + N节,却只切出 1 段、且段车数(55)≠ 标注节数(丰收 5)"的兜底告警**,于是 55 车被静默贴成丰收散运而无人拦。

## ④ 修复方向建议(后续走工单,本次不改)

1. **直接堵口(数据/流程)**:让「环球信任」在途批次 `bb15b6b0`(pending_freight)产出 active match rule —— 修复/补跑 `refresh_release_dispatch_match_rules()`,使 pending_freight 批次按 L904-906 映射真正落 active rule(根治"批次卡 pending_freight 不推进"那条既有 issue)。两船都有 active rule 后,**同样的单重跑就会切成 2 候选(5/50)**。

2. **拆分判据增强(`_split_payload_by_ship_rules`)**:锚点不要只认 `status='active'`。建议
   (a) 同时纳入近窗口 `completed` rule 的 ship token 作为"识别用"锚点;或
   (b) 直接从 `cargo_info_raw` 抽"船名 + N节"对(单子里 token 已具备),即使没有 rule 也能识别出"≥2 船";命中第二船但无 rule 时,**建 pending_review 候选**(而不是静默并入第一船)。

3. **一致性兜底告警**:当只切出 1 段、但单内出现 ≥2 个不同船名 token,或 `footer.zhuangche_jieshu`(55)≠ 标注节数(丰收 5)时,强制 `requires_manual_review`,杜绝整 55 车静默贴成单船。

4. **车级权威**:拆分只定"分船+节数",**逐车归属交 95306 窗口反查**(95306-window-reconcile-rule),不要依赖通知单标注行位置切连续段(避免重蹈 2026-06-27 抓错车)。

### 与九三散粮拆船的异同
- **中唐(整车铁矿粉)**:拆船在 **OCR/ingest 上游**,`agent._split_payload_by_ship_rules`(#130),按 `release_dispatch_match_rules` 的**船名 token** 切 payload 行 → N 候选;**不使用** `bulk_loading_notice_wagon`(故你查它为空是对的,本就不该有)。车级权威 = 95306。
- **九三(散粮)**:拆船在 **95306 ingest 下游**,`scripts/sync_jiusan_bulk_wagons.py` 按外部台账 **`bulk_loading_notice_wagon`(港方简装车通知单,ydid→船)** 把每车路由到对应船的 lot。是另一套机制。
- 结论:**本单确属中唐检装车上游拆分路径,不是九三台账路径**;根因不在台账、在 active rule 缺失致单锚点。
