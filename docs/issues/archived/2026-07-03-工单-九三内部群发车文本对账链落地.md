# 工单:九三内部群发车文本对账链落地

状态：已处理
## 背景

九三大豆项目每日有两类对账点:

1. 跟 `九三大豆发运群` 对账,读取每日晨报,更新循环车组看板底层快照。
2. 跟 `铁晟大豆业务内部沟通群` 对账,核实每日发车情况。

检查发现第 1 条已通过 `jiusan_morning_report_ingest.py` 定时执行;第 2 条只完成了文本识别和 `workflow_task_db` 建任务,但九三 `departure_flow/detect_departure_message` 被落为 `generic_sop_task`,没有真实执行器,因此不会自动写入 `bulk_loading_notice_wagon` 也不会触发散粮同步纠正。

## 问题

典型文本:

```text
八道 50节 新台子 大豆 诚信
七道 新台子 大豆 诚信  5节，45节 美国  K车
```

当前系统表现:

- 消息能进入 `message_inbox`。
- 能识别为 `sop_project_id=jiusan`, `sop_flow=departure_flow`。
- 但任务类型为 `generic_sop_task`,没有业务执行逻辑。

结果是发车文本不能成为 `ydid -> ship_name` 的台账事实源,后续 `sync_jiusan_bulk_wagons.py` 只能按既有台账或兜底船处理。

## 处理目标

1. 九三 `departure_flow/detect_departure_message` 应分配真实任务类型。
2. 单船发车文本应自动:
   - 解析股道、车数、船名、日期;
   - 从 95306 找到同日高桥镇 -> 新台子大豆整车票;
   - 数量一致且无台账冲突时写入 `bulk_loading_notice_wagon`;
   - 触发 `sync_jiusan_bulk_wagons.py --apply` 完成分船路由。
3. 多船混合文本在没有车号级拆分依据时,不得按 95306 制票顺序硬拆,必须输出人工复核原因和候选票,避免再造错账。

## 验收

- [x] 九三内部群发车文本不再生成 `generic_sop_task`。
- [x] 单船文本可自动落 `bulk_loading_notice_wagon`。
- [x] 单船文本执行后会触发散粮同步。
- [x] 多船混合但缺车号级依据时明确 `manual_review_required`,不静默 pending。
- [x] 覆盖测试通过。

## 处理结果(2026-07-03)

- 新增 `src/sop_hub/sop/jiusan_departure_reconcile.py`。

- `workflow_task_executor._update_message_inbox_status()` 改为优先按 `message_inbox_id` 精确更新,避免同名 `message_id` 跨群误伤。
