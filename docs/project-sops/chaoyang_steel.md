## 3. 术语定义

| 术语 | 说明 |
|---|---|
| 出港计划通知单 | 形成放货批次的主要材料 |
| 合同信息 | 项目执行的基础约定，包括委托方、承运人、货物、流向、价格等 |
| 补充协议 | 对主合同条款的追加或修正，按登记时间和生效规则更新项目当前执行条款 |
| 船名 | 出港计划中使用的船名或装运船名 |
| 批次时间窗口 | 用于辅助区分同到站、同船名下多个放货批次的计划时间、通知时间或相近作业时间范围 |
| 到站 | 检装车分块的重要锚点；朝阳项目的固定或常用到站待确认 |
| 放货批次 | 业务委托方下达的铁运计划，约定货物、船名、货量、运输方式、到站、计划起运时间等发运条件 |
| 返库 | 从铁路站台将未装车货物返回运输到港口堆货货场。返库会使港存数量增加、可发运数量减少。不要把“铁路发运/铁路返库”文字误判为已发生返库业务 |
| 发车数据 | 货物完成铁路装车后形成的发运记录，包括作业时间、作业道线、车型、车数、车号等信息。检装车通知单是当前获取发车数据的主要来源 |
| 发运报表 | 发车数据正式入库后，按指定 Excel 模板生成的朝阳钢铁发运表 |
| 发运报表模板 | `/Users/qicai21/projects/repos/sop-data-hub/config/report_templates/cysteel_departure_report_template.xlsx`（待补齐；当前仓库未包含该模板文件） |
| 发运报表文件名 | `锦州港铁矿发运表_<车数>_<日期>.xlsx`，其中车数取本次已入库有效车辆数，日期取本次报表生成日期或业务确认日期 |
| `departure_records` | 发车汇总记录，通常对应一次检装车通知单处理后的批次发车结果 |
| `wagon_shipments` | 单车发运明细，一辆车一条记录，用于保存车号、车型、到发站、95306 校验状态、运抵状态等单车事实 |
| 车号 | 95306 校验和发车记录的重要事实字段 |
| 郭东北 | 当前测试开发阶段的发运报表接收联系人，不是群聊，也不是群内 @；本 SOP 中为暂定报送对象 |
| 补充数据源 | 用于补发漏处理材料的数据入口，例如 `数据单发群` |
| `[GROUP001]` | 铁晟业务工作群的检索标识。方括号是查询协议的一部分，不能省略 |
| 朝钢铁矿发运群 | 正式运行阶段的发运报表报送群；当前不作为本项目监听或跟踪数据源 |

## 4. 数据源与群

| 来源类型 | 群 / 系统 | 消息类型 | 作用 | 是否主来源 |
|---|---|---|---|---|
| 主来源 | 铁晟业务工作群（`[GROUP001]`） | 出港计划通知单、检装车通知单 | 放货批次建立、检装车匹配、发车通知 | 是 |

说明：
- 本 SOP 中的群均作为数据来源描述。

- `数据单发群` 用于补发漏处理材料，默认只完成接收、下载、落盘和记录。
- 同一条补充材料是否进入朝阳钢铁主链路，必须由 agent 或项目 SOP 显式指定。
- `朝钢铁矿发运群` 当前没有需要监听或跟踪的信息，不纳入本项目监听任务。
- 当前测试开发阶段，发运报表只发送给微信联系人“郭东北”（暂定）；正式运行阶段发送到“朝钢铁矿发运群”。

## 5. 节点定义

### 5.1 合同信息登记与更新

| 字段 | 内容 |
|---|---|
| 输入 | 用户手动提供的文本信息、合同文件、补充协议文件 |
| 触发条件 | 用户明确要求 agent 录入或更新合同信息 |
| 处理动作 | 保存合同或补充协议文件路径；抽取并登记合同要素，包括委托方、承运人、货物、流向、到站、运输方式、价格等 |
| 输出 | 合同信息、合同要素条款、当前生效条款 |
| 入库表 | `business_contracts`（暂定，具体表名待实现确认） |
| 下一节点 | 放货批次建立或更新 |
| 允许补充数据接续 | 是。签订补充协议时，由用户提供给 agent 录入数据库，并更新当前生效条款 |
| 人工介入条件 | 新合同录入、补充协议录入、合同要素冲突、价格或流向变更 |

说明：
- 同一个项目可以有一个主合同和多个补充协议。
- 补充协议按独立记录逐条登记，不覆盖历史合同记录。
- 项目当前执行价格和约定条款，应按主合同加已生效补充协议计算得出。
- 放货批次创建和更新时，应引用当前生效合同条款。

## 6. 规则与优先级

### 6.1 合同规则

- 合同信息是项目执行的基础约束，放货批次应关联当前生效合同或合同条款。
- 合同要素至少包括：委托方、承运人、货物、流向、到站、运输方式、价格。
- 主合同和补充协议都应逐条登记，不能只保留最终覆盖结果。
- 补充协议生效后，后续放货批次、价格和约定条款按最新生效条款执行。
- 历史批次原则上保留当时适用的合同条款；是否追溯更新由人工明确指定。

### 6.2 数据来源规则

- 群只表示数据来源，不表示项目归属。
- 铁晟业务工作群是当前已确认的主来源。
- 朝钢铁矿发运群当前没有需要跟踪的信息，不作为监听来源。
- `数据单发群` 是补充来源，用于补发漏处理材料。
- 来自 `数据单发群` 的材料必须由 agent 显式指定项目和节点，才能进入朝阳钢铁链路。

### 6.3 放货批次规则

- 朝阳钢铁项目的放货批次必须从“出港计划通知单”创建。
- 文字消息不作为本项目自动建批来源；如文字中包含人工说明，只能作为原始消息、人工备注或异常说明保存。
- 后到的出港计划或人工确认材料用于补齐字段或修正候选批次，不应重复创建同一批次。
- 最低建批字段为：到站、货量、船名信息、批次日期。
- 船名信息无特殊指定时，以出港计划通知单识别出的船名为准。
- 批次日期以出港计划通知单为准，具体取“备注”栏中计划下达语句的日期，例如“4 月 1 日第一次下达计划：1000 吨（铁路）”中的“4 月 1 日”。
- 合同、运输方式、货物品类等字段用于补齐和提高匹配准确度；缺失时可先创建候选批次，但后续应补齐。
- 放货批次不能仅凭“到站 + 船名”唯一确定。同一到站、同一船名下也可能存在多个放货批次。
- 严格区分批次时，优先使用出港计划通知单中的批次日期、批次序号、数量、到站、船名和货物信息。
- 可使用相近时间作为辅助区分条件。时间字段包括计划起运时间、出港计划日期、检装车作业时间等。
- 批次匹配应采用组合判定：项目/合同候选 + 到站 + 货物 + 船名 + 数量 + 批次日期/时间窗口。任一字段不足以单独作为唯一判定依据。
- 当组合判定仍产生多个候选批次时，系统应挂起并要求人工确认，不得强行归并。
- “返库”是独立业务状态，不等同于铁路发运。只有出现明确的返库事实、返库数量或人工确认时，才可标记返库。
- 合远 9 当前按正常发运处理，不应因备注中出现“铁路返库”字样就判定为返库业务。
- 如果出港计划备注中数量不明确，但后续补充的检装车通知单能够提供有效车号、车数、到站和船名，可由 agent 指定接续到合远 9 的候选放货批次，用于补齐批次发运事实；正式货量仍需来自出港计划、人工确认或后续明确材料。

#### 6.3.1 放货批次字段来源与修正规则

| 字段 | 首选来源 | 可补充来源 | 修正规则 | 人工确认条件 |
|---|---|---|---|---|
| 到站 | 出港计划通知单 | 合同背景、人工补充 | 以出港计划通知单读取值为准；朝阳项目合同背景约定到站待确认 | 出港计划到站与合同背景不一致、OCR 疑似误识别 |
| 货量 | 出港计划通知单 | 人工补充 | 以出港计划通知单为准 | 出港计划缺失货量或 OCR 疑似误识别 |
| 批次日期 | 出港计划通知单备注栏 | 人工补充 | 以备注栏计划下达日期为准，例如“4 月 1 日第一次下达计划：1000 吨（铁路）”中的日期 | 备注栏日期缺失、日期冲突、OCR 疑似误识别 |
| 船名 | 出港计划通知单 | 人工补充、后续图片 | 无特殊指定时，批次船名以出港计划通知单识别值为准 | 船名缺失或与既有候选批次冲突 |
| 货物品类 | 出港计划通知单 | 人工补充 | 用于粗分类和匹配校验，不直接覆盖货物品名 | 与货物品名无法对应 |
| 货物品名 | 合同信息 | 人工补充 | 用于合同和批次匹配 | 与货物品类冲突 |
| 运输方式 | 出港计划通知单 | 合同信息、人工补充 | 当前草案按铁路发运处理；如朝阳项目存在其他运输方式，应由合同或出港计划确认 | 与合同约定或出港计划不一致 |
| 返库状态 | 明确返库通知或人工确认 | 后续业务材料 | 默认不是返库；仅在明确出现返库事实和数量时记录返库 | 仅出现“铁路返库”等易混表述、未说明是否实际返库 |
| 合同引用 | 合同信息 | 人工确认 | 建批后可补齐合同候选；确认后锁定当前适用合同条款 | 多个合同候选或补充协议影响价格/流向 |

字段更新原则：
- 首次建批允许字段不完整，但必须满足最低建批字段。
- 后续材料主要用于补齐字段，不默认覆盖已有字段。
- 后续来源可信度更高或用户明确指定时，允许修正字段，并记录原值和来源。
- 涉及合同、价格、到站、货量、批次日期的冲突，必须人工确认。
- 涉及“返库”的判断必须保守处理；不能仅凭关键词自动减少发运货量或改变批次性质。

### 6.4 检装车分块与匹配规则

- 到站是检装车分块的主要锚点；朝阳项目重点到站待确认。
- 船名用于缩小候选批次范围，但不能单独决定批次。
- 货名/货物品类用于辅助匹配和冲突检查。
- 时间窗口用于区分同到站、同船名、同货物下的多个批次。
- 节数用于验证，不作为主匹配依据。
- 当前建议匹配优先级为：到站 > 船名 > 批次日期/时间窗口 > 货物 > 数量/节数校验。
- 多个候选批次同时匹配时，系统应挂起并要求人工确认。

### 6.5 缺陷车规则

- 缺陷车先剔除，再统计有效车号和有效车数。
- 缺陷词表维护在 `sop-data-hub/config/inspection_defect_terms.yaml`，代码和 agent 不应另行硬编码。
- 当前确认词包括：排、空排、临修、地板漏、车皮毛刺、双划不入槽、车皮上沿开裂、车皮立柱开焊、小门划缺失、地板起皮、折页开焊。
- 缺陷车不得进入有效 `wagon_shipments`。
- 缺陷车应保留在异常说明或缺陷记录中，便于人工复核。

### 6.6 发车与报送规则

- 检装车通知单是发车数据的主要识别依据。
- 发车数据必须先完成批次匹配，再进入 95306 校验。
- 95306 校验失败的车辆不得标记为通过。
- 发车数据正式入库后，必须先制作发运报表，再进入报送动作。
- 发运报表模板固定为 `/Users/qicai21/projects/repos/sop-data-hub/config/report_templates/cysteel_departure_report_template.xlsx`（待补齐；当前仓库未包含该模板文件）。
- 发运报表文件名固定为 `锦州港铁矿发运表_<车数>_<日期>.xlsx`；车数取本次已入库有效车辆数，日期取本次报表生成日期或业务确认日期。
- 当前测试开发阶段，发运报表发送给微信联系人“郭东北”（暂定）。
- 正式运行阶段，发运报表发送到“朝钢铁矿发运群”；群检索标识待确认，确认后必须保留方括号。
- 发送失败不回滚业务入库，只记录发送失败状态并允许重试。

### 6.7 幂等规则

- 同一图片重复处理不应重复创建放货批次或发车记录。
- 同一车号在同一批次内重复出现时，应挂起或合并为一条有效车辆记录，具体策略待确认。
- 同一发运报表重复生成或重复发送应有报表记录和发送记录约束，避免重复通知。

## 7. 异常处理

| 异常 | 处理方式 | 状态建议 | 是否允许继续 |
|---|---|---|---|
| 图片未下载成功 | 保留消息记录，标记待拉图重试 | `pending` | 否 |
| OCR/VLM 识别失败 | 保留原图和错误原因，进入人工复核 | `suspended` | 否 |
| 合同信息缺失 | 可暂存候选批次，但不能确认最终合同价格和约定条款 | `pending` / `suspended` | 可继续收集材料 |
| 合同要素冲突 | 保留主合同和补充协议记录，等待人工确认当前生效条款 | `suspended` | 否 |
| 出港计划关键字段缺失 | 建立候选记录或挂起，等待补充材料 | `pending` / `suspended` | 否 |
| 返库表述不清 | 保持正常发运候选，不自动标记返库；等待人工确认或明确返库材料 | `pending` / `suspended` | 可继续收集材料 |
| 补充文字无法归类 | 原文落库，只作为人工备注或待处理材料，不进入自动建批 | `pending` | 可继续处理其他材料 |
| 到站识别不到 | 不进入批次匹配，等待人工确认 | `suspended` | 否 |
| 朝阳项目到站疑似 OCR 误识别 | 标记人工复核，不自动归入任何固定到站 | `suspended` | 否 |
| 缺陷车标记不清 | 保留候选，不写入有效车辆 | `suspended` | 否 |
| 放货批次匹配不到 | 标记待处理，不可强行归并 | `suspended` | 否 |
| 多个候选批次同分 | 输出候选列表，等待人工确认 | `suspended` | 否 |
| 95306 查不到车号 | 记录失败原因，不标记通过 | `failed` / `suspended` | 可继续处理其他车辆 |
| 发运报表模板缺失 | 保留入库发车数据，记录失败原因；等待人工补齐模板路径或模板文件 | `failed` / `suspended` | 否 |
| 发运报表生成失败 | 保留入库发车数据，记录失败原因 | `failed` | 否 |
| 开发报送对象发送失败 | 业务记录不回滚，发送状态单独失败并允许重试 | `failed` | 是 |
| 生产报送对象发送失败 | 业务记录不回滚，发送状态单独失败并允许重试 | `failed` | 是 |
| 补充数据未指定项目/节点 | 只落盘，不进入业务链路 | `pending` | 否 |

  - 文件名模式：`锦州港铁矿发运表_{wagon_count}_{date}.xlsx`
- [ ] fixture 能被 `sop-data-hub` 的项目 SOP loader 正确解析，且 `report_targets`、`report_artifact` 不丢失。

### 9.2 放货批次验收

- [ ] 给定一份主合同，系统能登记合同文件路径和合同要素。
- [ ] 给定一份补充协议，系统能作为独立记录登记，并更新当前生效条款。
- [ ] 放货批次能关联当前生效合同或合同候选。
- [ ] 同一到站、同一船名、同一货物下出现多个相近批次时，系统不能只靠“到站 + 船名”强行归并。
- [ ] 批次日期能从出港计划通知单备注栏计划下达语句中提取，不能默认使用消息收到日期覆盖。
- [ ] 给定一张朝阳钢铁出港计划通知单，系统能生成或更新 `release_batches`。
- [ ] 合远 9 备注中的“铁路返库”字样不会被自动判定为已发生返库业务。
- [ ] 文字消息不会自动生成或更新 `release_batches`。
- [ ] 重复导入同一出港计划，不重复生成批次。

### 9.3 检装车与匹配验收

- [ ] 给定一张包含朝阳项目确认到站的检装车通知单，系统能按到站分块。
- [ ] 缺陷词表从 `sop-data-hub/config/inspection_defect_terms.yaml` 读取，不从代码或 agent 文档硬编码。
- [ ] 缺陷车不会进入有效车辆列表。
- [ ] 船名能辅助匹配具体放货批次。
- [ ] 节数只用于校验，不作为主匹配依据。
- [ ] 匹配不到批次时，系统挂起，不强行写入正式发车记录。

### 9.4 95306 与入库验收

- [ ] 95306 校验通过的车辆能写入 `wagon_shipments`。
- [ ] 95306 校验失败的车辆不能标记为通过。
- [ ] `departure_records` 写入正确批次、车数和车号。
- [ ] 同一车号重复处理不会重复写入。

### 9.5 发运报表与发送验收

- [ ] 发车数据入库后能使用 `/Users/qicai21/projects/repos/sop-data-hub/config/report_templates/cysteel_departure_report_template.xlsx` 生成发运报表；该模板文件需先补齐。
