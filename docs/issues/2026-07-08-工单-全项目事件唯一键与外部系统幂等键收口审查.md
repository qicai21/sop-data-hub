# 工单:全项目事件唯一键与外部系统幂等键收口审查

- **状态**：待处理 — 架构收口审查，跨项目 car_no 单键仍需系统化

- 日期: 2026-07-08
- 类型: 缺陷修复 / 架构收口 / 回归加固
- 优先级: 高

## 背景

朝钢 `马兰幸福` 22 车事件暴露出一个更底层的问题:

1. 同一项目、同一批次内,车号会跨不同发车事件复用;
2. 若链路里把 `car_no` 当成:
   - 事件唯一键
   - 上传幂等键
   - 门户反查唯一键
   则一旦出现复用车号,就会把旧趟数据误判成“本次已存在/本次已上传/本次已核对”;
3. 当前系统虽已在部分链路切到 `ydid` 或 `box_no|car_no`,但仍存在项目间口径不一致、局部 fallback 回退到 `car_no` 的情况。

这不是单个项目的偶发问题,需要按项目全量审查并收口。

## 目标

按四个 SOP 项目逐一确认:

1. 哪些链路已经使用正确的事件级键,无需改;
2. 哪些链路仍以 `car_no` 作为单键判定标准;
3. 哪些地方允许 fallback,但 fallback 口径需要更严格;
4. 最终沉淀统一规则,并补稳定测试。

## 统一口径(拟定)

### 1. 整车项目

适用: `chaoyang_steel` / `zhongtang_special_steel`

- 事件事实唯一键: `ydid`
- 事件分组锚点:
  - `source_message_id`
  - 或列车编组号
  - 或 95306 制票时间窗口
- `car_no` 只能作为展示字段、排序字段、人工核对字段;
- 不允许把裸 `car_no` 当作跨事件唯一身份。

### 2. 集装箱项目

适用: `jilin_jingang_jinzhou` / `jiusan`

- 入库事实唯一键:
  - 吉林优先 `box_no|car_no`
  - 九三优先 `ydid` / `hph+box_no`
- `car_no` 不可单独作为上传反查或事实去重键;
- 仅在“当前事件范围已先被更强键收窄”后,才允许作为辅助筛选字段。
