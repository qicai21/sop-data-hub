# 业务铁律:朝阳钢铁系统上传必须紧跟反查

> 写入时间:2026-06-02
> 来源:朝阳钢铁项目跟鞍钢门户 ansteel(`56.ansteel.com.cn`)对接

## 规则

向朝阳钢铁系统(鞍钢门户)**写入**任何 wagon 数据后,必须**在同一进程内立刻调用查询接口确认数据落地**。一致才算成功,不一致或反查失败必须 retry / 报警。

```
upload_wmwm19_ins_v(53 cars)
  → sleep 2s
  → query_wmwm19_inq_v(same plan)
  → 拿返回的 wagon set
  → 跟上传的 53 cars set 比对
     ├── 完全一致 → ✅ 标 success
     ├── 缺失 (missing) → ❌ retry / 报警
     └── 多出 (extra) → ⚠️ 异常,报警
```

## 为什么必须这样

1. **朝阳系统的删除粒度是"列"不是车** — 用户实测:删 2 车,整列(53 车)被删。意味着上传也可能"看似成功实际整列被覆盖/丢失",必须反查才能确认。
2. **网络/服务端任何瞬时问题** — flag=0 + msg="Successful call!!" 并不保证数据真的在 DB 里,只有反查才能确认。
3. **业务对账** — 后续若发现网站车号少了,可以从我们 DB 这边的 upload log 反推哪个 batch 出问题。

## 落地位置

- **yaml**: `config/project_sops/chaoyang.yaml` → `flows.consignee_upload_flow.upload_after_verify: true`
- **代码**: `src/sop_hub/external/chaoyang_ansteel/upload_wagons.py` → `upload_and_verify()` 函数内置 verify,不暴露"只 upload 不 verify"的入口
- **chain 集成**: `src/sop_hub/sop/workflow_task_executor.py._execute_chaoyang_inspection_chain` step 6c 自动调,与 step 6b (excel 发微信群) 并行执行(不冲突,两个下游都做)

## 上传 vs 发 excel 是 2 个独立动作

- **发 excel 到微信群**:给"人"看的 — 数据单发群 / 朝钢铁矿发运群,人工对账用
- **上传到鞍钢门户**:给"系统"看的 — 收货端业务系统直接入库,跟我们 DB 双向闭环

两个都要做,**不允许二选一**。chain step 6b + 6c 都执行,任一失败都报警。

## 反查时机

- 上传立刻反查 → sleep 2s(给服务端处理时间)→ query → 比对
- 长期可以:每个 release_batch 上传完成后 N 分钟、N 小时再反查一次,看车有没有被"列粒度"误删

## 失败处理

- **missing != []** → 上传不完整,记 log,自动 retry 一次,仍失败 → wx-ui-bridge 通知 [郭东北]
- **extra != [] 且 WAYBILL_TIME 是今天** → 网站多了"我们没上传的车",异常,通知人工 — 可能其他人也在上传,或之前上传残留
- **登录失败 / signature 过期** → upload_and_verify 内部已经处理(login 内置 session)
- **wmwm01 查不到 plan** → 立即 fail,不进上传步;原因:plan 还没建,要么 ship_name 拼错,要么对方系统延迟
