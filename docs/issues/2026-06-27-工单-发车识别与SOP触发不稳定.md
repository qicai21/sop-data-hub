## 问题 2:数据单发群输出消息自触发 → 反馈环(已修)

**实测**:#420 的输入文本**就是系统自己发到数据单发群的超时告警**("⚠️ 检装车文本触发器超时...贝拉 汐子 预期 36 节")→ 含"船名+N节"→ 被 `text_router` 当发运文本重新触发新的 inspection_text_trigger → 又等不到车 → 又告警 → **自激死循环**(贝拉36车6-25早发完,95306汐子6-26/6-27制票0车)。另有人在铁晟群随口问"贝拉"也触发。

**根因**:数据单发群是**系统输出/屏障群**(只有用户+我,无客户),系统的告警/合成通知/excel伴随消息被重抓,`text_router` 不区分输入/输出 → 自触发。

**修复(已做,代码)**:`src/sop_hub/sop/text_router.classify_text_message` 加双闸——① **数据单发群消息一律不当触发源**;② **⚠️/✅ 开头的系统告警/通知跨群兜底忽略**。19 测试通过,真发运文本不受影响。+ 取消 spurious #420、标 7 条数据单发群告警为 ignored,断当前循环。

## 根因 + 系统性分析(反复同构缺陷,本工单第二次记录)

两个问题归到两条**反复出现**的架构缺陷:

| 缺陷 | 表现处 | 现状 |
|---|---|---|
| **A. 依赖项 later 就绪时,挂起/0结果不自愈重试** | 吉林发运文本(本工单)、中唐货运(`2026-06-27-中唐货运`首单)、出港0批次 | 检装车rendezvous/waiting_media已补;**发运文本/中唐货运/出港0批次还裸** |
| **B. 输出/屏障群消息被当输入重新触发(反馈环)** | 贝拉重复告警(本工单)、中联发 spurious(早前) | **本工单已修**(text_router 双闸) |
| **C. `create_wagon_shipments` 按 car_no 跨 batch 去重,吃复用车号** | 吉林40车只建24(本工单)、马兰61节、[[create_wagon_shipments_two_gaps]] | ✅ 改 ydid commit b2a22ef |
| **D. 改了代码长驻 daemon 不热重载,继续跑旧逻辑** | 本工单(text-watch 跑旧 car_no 半天)、[[key_daemons_and_restart]] | **改 sop 代码后必 kickstart 重启对应 daemon**;尤其 `text-watch --run-chains` 才是发运/检验链执行体,不是 live-service |

**排查教训**:
1. 问题1 一度误判为"rail sync 滞后",**用户纠正**后核实 rail 库 05:00 就齐 40 车——**遇"数据不全"先核实数据源时间戳,别甩给 sync**。
2. "改了代码没效果"耗了最久:**长驻 daemon 不热重载**。判别法=**in-process/隔离跑(fresh 进程)对、长驻 daemon 错 → 一定是 daemon 没重启**(临时 `result.warnings.append("探针")` 一验便知)。且要重启的是**真正执行链条的 daemon**(`text-watch --run-chains`),不是恰好也 log 了 text_router 的 live-service。

**A 的统一解(待排期)**:抽一个「pending-rendezvous + 制票/批次就绪回扫」小框架——发运文本/检装车文本/中唐货运 挂起后,当 95306 制票 或 批次进 pending_freight 时回头重匹配,别每处各写。这是把"发车识别不稳定"根治的关键。

## ⚠️ 控制边界教训(点1,最重要)

**`run_departure_executor_chain` 没有 dry/apply 开关。只要 `create_wagon` safe_to_apply,step5-6 无条件:生成 excel → 上传工厂门户 → 发微信(数据单发群)。verify(5b)只事后记录,不门控发送。**

排查 ydid/daemon 问题时,我把"重跑链条看 create_wagon"当成可反复试探的查询——cursor reset 重触发 + in-process 脚本——**真发了微信 6 次**(5×24车 + 1×40车,数据单发群屏障群,无业务损失)。我误读 `excel_sent: None` 以为没发。

**二次纠正(用户追问"工厂系统没数据"后)**:我又把"真上传工厂门户 6 次"说错了——**工厂上传 0 次**。`5_factory_upload.login_success=False`、`login_error="必备字段不全(货票号缺40,标重缺40)→挂起待95306补齐,暂不上传"`,登录前就被拦,根本没连工厂。**两次都是没读全 preview 字段就下结论**(第一次漏看 step6 sent=True,第二次漏看 step5 login_success=False)。教训升级:**对外动作的"到底发没发/传没传",必须逐字段读执行结果,不靠单个字段或印象。**

**铁规矩(已立)**:`run_departure_executor_chain` / 触发 daemon 重跑 = 对外发送+上传,**绝不用于诊断**。诊断只跑隔离单函数(create_wagon / find_release_batch / verify 单独跑,不进链条)。判断"链条会不会发"先读 step5-6 有无门控,别靠 preview 字段猜。
