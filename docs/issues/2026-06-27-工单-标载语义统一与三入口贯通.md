# 工单:wagon_shipments 标载语义统一 + 三个提取入口贯通

- **提出日期**:2026-06-27
- **类型**:数据模型缺陷(字段语义不清 + 多写入口各写各的)
- **状态**:✅ 已完成(代码 + 全表数据 + 记忆)
- **起因**:从"吉林40车工厂上传被拦(缺 hph/标重)"一路深挖,发现 `marked_weight` 既缺失又语义混乱。

---

## 一、现象 vs 真相

**现象**:工厂上传校验"标重缺";全表查 marked_weight 大面积缺(wagon 缺4168、box 缺1236),且同型号值不一(C64K→60/61/64、集装箱→64/54/31/3.55)。

**真相(经用户校准)**:
- **标载 = 标重 = 计费重量,是同一属性的多个叫法**(整车按标载计费,不另过磅,**无独立"实际称重"**)。我一度误判为"marked_weight 是随货变的实际重量、不是标载",错。
- 95306/rail 的 `marked_weight` 列**就是**标载,但**有噪声(同型号偶现异常值)+ 整段缺失**(如老中唐车为 None),直接搬不可靠。
- 标载本质是**车型属性**,应从 `car_model` 推权威值。
- **配载吨**(C70=69.5t 这种 planned 装载,在 `cargo_load_plans.yaml`)是另一回事,跟标载对账看涨吨/亏吨。

## 二、即时修复(已做)

集装箱/平板车(X70·NX70)→64(敞顶箱);C70系→70;C64系(C64K/C64H/C64T)→61;C60/C62系→60;散粮车L系(L18/L70)→60。规则经用户逐条确认。

1. **全表回填**:wagon_shipments 11219 车标载齐(70:6333/61:2324/60:1632/64:930)、车号(ydid)100%、hph 100%、car_model 补413;wagon_container_shipments 6666 箱加 hph 列 + 标载全 64。
2. **marked_weight 语义统一为标载**(选 B,省混淆);中唐计费走 `zhongtang_dispatch_map.actual_weight` 另表,不受影响。

## 三、根因 + 系统性分析(多写入口各写各的)

**反复缺陷:同一字段有 ≥3 个写入口,各自手搓、口径不一。** 标载/hph 三个提取入口:

| 入口 | 用途 | 修前 | 现状 |
|---|---|---|---|
| `build_wagon_row` | ingest_wagons(九三sync/手工/backfill) | marked_weight=rail计费值、hph已写 | ✅ commit c3e8c59 走车型推标载 |
| `create_wagon_shipments`+chain | 吉林发运链 | 只写精简行,不落 | ✅ commit e588467 同run回填(提取时,非定期) |
| `workflow_task_executor` 手搓INSERT | 朝阳/中唐检验链 | marked_weight=rail计费值、**完全没写hph** | ✅ commit 3292572 加hph+走车型推标载 |

**规律**:wagon_shipments 写入口分散(违背 [[wagon_ingest_unified]]「一律走 ingest_wagons」),导致字段口径漂移。本次三处收敛到同一 `marked_load_from_car_model`,**提取时即写 hph+标载,不靠任何事后回填/定期 sync**(用户明确要求:从95306提取到wagon_shipment时就同步,不是定期回填)。
