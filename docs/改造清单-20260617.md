## P2a — 先做(韧性 + 正确性,低风险)

### 1. wx_config 导出自动化（去掉手动脱节）  · M · 风险:中
- **现状**:`config/project_sops/*.yaml` 的监听群要手动 `wx_config_exporter` 导出成 `wx-ops-agent/data/runtime/wx_config.json`,daemon 读 json;改了 yaml 忘导出 → daemon 用旧路由,**静默错路由**。
- **方案**:把导出挂到 yaml mtime 监听(复用 `sop_watcher` 热加载),或 daemon 启动时校验 json 与 yaml 一致、不一致即告警/自动重生成。两边都缺时硬报错(现在是静默兜底)。
- **收益**:消除"改了配置不生效"这一类最隐蔽的故障。

### 2. actual_wagon_count 的 ydid-NULL 兜底  · S · 风险:低
- **现状**:`shipped_weight.py` 的 `actual_wagon_count = COUNT(DISTINCT ydid)`(今天为修散粮复用车改的)。若某批 ydid 为空,会算错/吞行。
- **方案**:`COUNT(DISTINCT COALESCE(NULLIF(ydid,''), car_no, id))` 兜底;并加一条数据校验:active batch 出现空 ydid 即告警。
- **收益**:防止历史/异常数据把车数算花。

### 3. 收货人门户重复上传 —— 台账日扫告警  · S · 风险:低
- **现状**:今天建了 `factory_upload_ledger.db`(箱号→门户ID),但只有第五趟 96 条;且查重要人工调 `find_duplicates`。门户"覆盖式 + 列表只显1条"会藏重复。
- **方案**:(a) 把前 4 趟现有门户ID 反查回填,建立完整基线;(b) 加一个每日 `find_duplicates` 扫描 → 有同箱多门户ID 就进晨报/告警;(c) 上传链已接台账,保持。
- **收益**:对方系统的重复记录我方可主动发现,不再靠对方反馈。

### 4. jilin 门户 verify-before-remove 强约束  · S · 风险:低
- **现状**:`factory_remove` 删除前不强制反查;今天人工删 246 条时靠我自己先反查。
- **方案**:remove 高层入口默认"先反查命中再删 + 删后复查条数下降",dry-run 默认开(代码已部分具备,补成硬约束)。
- **收益**:防误删收货人系统数据。

### 5. 凭据集中（停止多处硬编码/重复）  · M · 风险:中
- **现状**:jilin 门户 `saibin/Xts@95306` 在 `factory_upload/verify/remove` **各写一遍**;朝钢鞍钢 `CWL20085/...` 硬编码在 external 模块。
- **方案**:统一到一个凭据加载点(env / 受保护配置),三处引用同一处;不入 git。
- **收益**:改密码改一处;降低泄露面。
- **依赖**:与 #7(朝钢)一起做更省。

## P2b — 次批(对齐声明与现实 / 上线动作)

### 6. 中唐 lifecycle 与上传流对齐  · M(补流) 或 S(降级) · 风险:中 · **需你拍板**
- **现状**:`zhongtang.yaml` 声明 `full_track_to_received`(跟到到货),但**没有门户上传流、没有跟踪流**,只有出 excel + 发群。声明与现实不符。
- **方案二选一**:(a) 若中唐确实要传收货人系统 → 补 `consignee_upload_flow`(参照朝钢/吉林);(b) 若中唐不需要上传、只到发运 → lifecycle 降为 `shipped_is_completed`,删掉跟踪声明。
- **要你定**:中唐到底要不要往某个收货人系统上传?

### 7. 朝钢鞍钢上传去脆化  · L · 风险:高(要对接真实环境验)
- **现状**:`external/chaoyang_ansteel/` 100% 硬编码、**login 重放固定 RSA 密文**——服务端一旦校验时间戳/nonce 即全链崩;凭据写死;无 yaml。
- **方案**:正经实现签名(实时加密,不重放),凭据集中(#5),端点/字段上 yaml(对齐 jilin 的做法);保留"上传必反查"铁律。
- **收益**:朝钢上传从"随时可能整体失效"变为可维护。**这是当前最脆的对外环节**。

### 8. 发送目标切到各项目业务群（上线）  · S · 风险:中(发错群面子事故)
- **现状**:jilin/chaoyang/zhongtang 的 `send_report.target_group` 都还压在测试群 `GROUP013`;注释写明上线应切 GROUP005/004/003。
- **方案**:确认各业务群已建好 + 群备注名带 `[GROUPxxx]` 搜索码 → 逐项目改 yaml target_group → 各发一条真表验证落对群。
- **要你定**:哪些项目现在可以正式上线发业务群?(可逐个切,不必一次全切)

### 9. waiting_media 975 积压根因  · M · 风险:中
- **现状**:`message_inbox` 975 行卡 `waiting_media`(等图片落地);疑似 wx-ops-agent 图文落地端积压(与之前"幽灵 pending 图驱动微信"同源)。
- **方案**:盘清 975 是哪些群/哪天/是否真有图未下;修图片 ledger 回写(之前 spawn 的 `task_87f2796e` 那条根因);清掉确实无图的僵尸 waiting_media。
- **收益**:消除图文管道积压,顺带止住无谓的微信驱动。

## P3 — 大改(架构,可缓)

### 10. 发车链做成 yaml 可配步骤注册表  · XL · 风险:高
- **现状**:发车链是 `executor_runner.run_departure_executor_chain` 里一个**大过程函数**(if/try 串),yaml 里那串 chain 字符串只是注释,**没有步骤引擎**。加/换步骤要改 Python。
- **方案**:抽象步骤注册表(每步 = 可注册的 node + 输入输出契约),链定义从 yaml `flows.*.steps` 真驱动;先在 jilin 试点。
- **收益**:链路真正"配置即定义",降低改链风险;但工程量大,排在最后。

### 11. 容器/整车双写原子性  · M · 风险:中
- **现状**:`create_wagon_shipments` 先写 `wagon_shipments` 再写 `wagon_container_shipments`,后者失败只 warn 继续 → 状态可静默劈叉。
- **方案**:同事务 or 写后对账(箱表车数 == wagon 表车数,不一致告警/自愈)。

### 12. daemon 监管 + 启动次序  · M · 风险:中
- **现状**:5 个 daemon 各自 KeepAlive,**无启动次序**;dashboard(tmux board)**不归 launchd 管,重启即失**;今天还出现过 text-watch 双实例抢锁。
- **方案**:board 纳入 launchd;加单实例保护(pidfile/锁,防双 text-watch);`restart_all.sh` 升级为带健康检查。
- **收益**:杜绝今天这种"多实例抢锁 + 空转 17 小时"。

### 13. zhongtang 检装车链失败(#145)  · M · 风险:中
- **现状**:9 条 `zhongtang_inspection_chain` 失败,`extraction JSON not found` / 候选空字段——纯图片多船 LIMIT-1 那类。
- **方案**:按记忆 [[inspection-payload-multi-group-split]] / [[inspection-text-trigger-arch]] 把纯图片多船拆 N 候选的残留补齐。
