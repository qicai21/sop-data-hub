# 九三大豆铁路发运项目 SOP

> 当前运行说明 v1.0；更新日期：2026-10-12。
> 项目入口：[00-START-HERE.md](../00-START-HERE.md)。程序配置：[jiusan.yaml](../../config/project_sops/jiusan.yaml)。
> 本文区分已运行能力、运营推算和实现限制；历史版本中的船舶数量、批次状态及费用单价不代表当前事实。

## 1. 项目定位

九三大豆项目（project_id：`jiusan`）负责进口大豆从锦州港装车，经铁路发往新台子，再交付九三铁岭工厂的运输事实、分船分票、发运进度及循环资源跟踪。

系统维护集装箱、散粮车两条运输支线。费用计算、辅助作业分配及结算单证由 sibling `fee_manager` 负责。

合同关联：`JGWL-JZTS-DD-202601`，甲方锦州港物流发展有限公司，乙方锦州新铁晟港口物流有限公司；合同有效期为 2026-01-01 至 2026-12-31。正式合同及有效费率以业务项目档案、费用侧合同管理为准，不以本仓历史 YAML 费用段作为当前结算依据。

## 2. 运输路线

| 运输方式 | 常规路线 |
|---|---|
| 集装箱 | 高桥镇 → 新台子 → 三三〇处专用线卸箱 → 汽运短倒至九三工厂 |
| 散粮车 / K车 | 高桥镇 → 新台子 → 九三集团铁岭大豆科技有限公司专用线卸货 |
| 得胜台补充路线 | 启用时由用户明确指认；当前常规同步脚本仅查询新台子，不能视为已自动覆盖 |

三三〇处专用线与九三工厂专用线是不同的接卸地点。铁路专用线属性以 95306 公示为准，不能把两者和得胜台简单合并。

## 3. 数据来源与职责

| 来源 | 用途 |
|---|---|
| 95306，`jz-port-super` 综合账号 | 运单、车号、箱号、车型、标载、制票及运输节点的铁路事实 |
| 用户提供的放货单及说明 | 确认船舶、放货日期、运输方式与计划货量 |
| 港方累计货票 Excel | 分船分票、核对发运数量；同票混船时精确到箱号 |
| 九三大豆发运群 `GROUP093` | 晨报、港内及三三〇资源盘点、累计发运报表 |
| 铁晟大豆业务内部沟通群 `GROUP094` | 每次发车的道线、车数、船名及混发说明 |
| 数据单发群 `GROUP013` / 用户会话 | 用户指认材料及补充说明入口 |

群名和文件名是来源信息，不能单独证明项目、船舶或批次归属。九三不以检装车通知单图片作为自动发运主入口。

## 4. 放货批次建立

用户明确放货后，归档原始通知单，建立或更新 `release_batches`。常规约定：`lot01` 为集装箱，`lot02` 为散粮车；历史仅有集装箱的船可以只有 `lot01`。

计划量采用用户确认的放货量。通知单分项、全船数量或用户说明不一致时，列出差异，由用户确认后落库。记录船舶、通知 / 放货日期、运输方式、计划量和原始材料依据。

放货指认与船舶元信息维护由用户 / agent 完成；不能将本项目写成已实现无条件自动识图建批。

## 5. 发运入库与分船

| 事实 / 台账 | 表 | 归属或计数锚点 |
|---|---|---|
| 集装箱运输事实 | `wagon_container_shipments` | `YDID + 完整箱号` |
| 散粮车运输事实 | `wagon_shipments` | YDID |
| 集装箱分船台账 | `container_loading_notice` | `YDID + 完整箱号` → 船舶 |
| 散粮车分船台账 | `bulk_loading_notice_wagon` | YDID → 船舶 |
| 放货批次 | `release_batches` | batch_id |

箱号和车号可以循环复用，不能按物理箱号或车号去重计算累计发运量；箱池统计则采用物理箱号口径，两者须明确区分。箱号保留完整前缀及七位数字。

归属更正需要同步修改台账和发运事实，再重算批次，防止下次同步把归属改回。混船货票按箱拆分，不能整票强挂同一船。95306 未包含的历史记录须单独说明来源和时间覆盖范围。

## 6. 自动同步与人工核对

九三同步每 30 分钟运行一次，从本地 95306 collection 读取事实，更新发运记录、运输状态和批次统计。入口为 `scripts/sync_jiusan_all.py`，分别调用集装箱和散粮车同步脚本。

内部群发车文本通过任务执行器进入核对链，可补充散粮车分船台账及道线；混发有冲突或无法确定具体车辆时，需要人工提供车号 / 箱号划分。

现有实现限制：

- 无台账时，集装箱存在当前船或车体上趟船名兜底，散粮车存在未完结船兜底；这些推断不能作为最终分票确认。
- 集装箱多船同时 loading 时不选择全局默认船，但仍存在车体上趟归属回退；车体跨船循环时需要核对。
- `scripts/jiusan_bulk_report_ingest.py` 的自动散粮 Excel 扫描目前仅覆盖“诚信、和谐1”，其他船不能假定已经自动回灌。
- 两个常规同步脚本当前以 2026-06-09 为查询起点；更早数据由历史补录与核验处理。
- YAML 中存在流程描述和旧费用段；不能据其声明认定所有节点均有运行实现。

## 7. 重量口径

看板已发货量当前按 YAML 估算：集装箱每箱 `28.4` 吨；散粮车 `L70` 每车 `69` 吨，其余每车 `61` 吨。

铁路 `marked_weight` 是计费标载，须独立保存；港口确认的过磅重量是实际业务确认重量。三种重量分别使用，不能互相替代。收入结算重量由用户提供确认依据，传给费用系统。

计划放货量与估算已发量出现超差时，先核查运输数量、分票及重量口径，不以估算超量自动认定多入库或应关闭批次。

## 8. 作业道线

优先采用内部群明确报告的道线，并规范化“7道 / 七道”等写法。历史缺失数据按用户确认补录。

已确认的历史补录规则：散粮车填七道；同日有散粮车装卸时，集装箱填八道，否则填七道。补录应记录依据，区别于现场明确报告；后续真实道线优先于该历史补录规则。

## 9. 每日晨间对账

每日北京时间 8 / 9 / 10 / 11 点尝试执行，当日成功一次后停止后续尝试。先读取晨报、形成箱池快照，再核对铁路事实、分票来源与本地记录。

当天无晨报时等待后续时点；缺少 Excel 可以完成检查并保留未确认归属，不应因周日无表而中断。`succeeded` 表示本轮检查执行完成，不表示差异全部清零；异常须查看对账结果和日志。

晨间统一任务与内部群发车文本核对是互补链路：内部文本由任务执行器处理，不能把晨间任务成功视为每条内部发车文本都已处理的证明。已有当日快照不会被晨报自动覆盖，人工修正须保留依据。

入口：`scripts/run_jiusan_morning_reconcile.py`。运行记录：`scheduled_reconcile_run_log`；箱池快照：`container_pool_snapshot`；逐笔更正：`reconcile_action_log`。

## 10. 循环看板

展示六个环节：

```text
港口空箱 → 港口重箱 → 在途（重）
新台子站 → 三三〇专用线 → 在途（返空）
```

每两小时按每列最多四车查询轨迹，覆盖前后半列。有历史出线依据时用于抽样分组，否则按当次制票顺序选择首车、前半末车、后半首车、末车；抽样位置不是已核实的实际编组位置。

部分车已入线、部分仍等待时，按线上作业展示；所有抽样车出线后展示返空，末次出线后十小时推算返港待装。返空及返港包含推算，不能视为全列实时定位。查询失败或使用旧样本时应检查缓存时间和错误信息。

车组调出须记录日期，不固定写死车组数量或箱池规模。资源池盘点、循环车组和累计发运量分别核对。运营变更记录见 [九三循环运营日志](../business-rules/jiusan_cycle_ops_log.md)。

## 11. 批次完成与费用联动

用户确认发完后标记 `all_loaded`；到货确认按完整生命周期继续推进：

```text
pending_freight → enriched → loading → all_loaded → tracking → delivered → confirmed_received → closed
```

新货不应分配给已发完批次，现有兜底中包含 `all_loaded` 等状态的行为属于实现偏差，需另行处理。运输到货与船批发完是不同条件，不能因为当前已发记录全部到货就认定剩余计划已发完。

批次、分票、道线和确认重量先在 SOP 校正并验证，再单向同步到 `fee_manager`。费用侧不得反向修改 SOP 运输事实。费率、费目与结算规则由费用侧维护，生成结算单前检查同步时间和结果。

代码或配置调整走工单、固定回归测试及 git；完成后检查并重启受影响的长驻服务，清理临时脚本。周期任务下一次启动加载新代码。文档修改须核对实现依据和内部链接；纯文档修改无需重启服务。
