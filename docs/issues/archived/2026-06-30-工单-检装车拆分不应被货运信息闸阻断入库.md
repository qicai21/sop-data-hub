# 工单:检装车拆分/车列入库不应被货运信息闸阻断

- **类型**:流程闸口缺陷
- **发现日期**:2026-06-30
- **发现来源**:中唐特钢 2026-06-29 检装车通知单 55 车复盘
- **状态**:已处理;由 2026-06-30 检装车主链三处高风险闸口整改覆盖
- **处理顺序**:3
- **严重度**:高 —— release_batch 已存在且检装车单能按船名+节数拆分时,车列事实应可先入库;缺货运信息应只阻断发运 Excel/发送/对外动作,不应阻断候选拆分和 95306 车列落库

## 背景

中唐特钢 2026-06-29 检装车通知单写明两船:

- 丰收散运 5 节
- 环球信任 50 节

95306 已能反查到本窗口 55 车发运事实。系统内对应 release_batch 也已存在,但当时环球信任 lot08 还缺货运信息,没有 active `release_dispatch_match_rules`,导致上游拆分只命中丰收散运,整张 55 车单被挂到丰收散运。

用户确认的新闸口原则:

- 没有货运信息,无法制作发运 Excel 是对的。
- 但 release_batch 已经建立、车列也能正确拆分时,不应影响数据入库。

## 现象

当前拆分/匹配链路把多个职责绑在同一个 open 状态闸上:

1. `_split_payload_by_ship_rules()` 只使用 active `release_dispatch_match_rules` 的船名 token 做多船拆分锚点。
2. `match_release_batch_by_ship_destination_cargo()` 只允许 `loading/enriched` 批次承接检装车候选。
3. 缺货运信息的批次处于 `pending_freight`,既不能成为拆分锚点,也不能承接候选。
4. 后续货运信息补齐、批次进入 `enriched` 后,系统不会自动回头重拆已经生成的旧候选。

结果:车列事实已经具备,但因为货运信息闸提前阻断,导致候选无法正确拆分/归属/入库。

## 期望设计

将链路拆成至少两层闸:

1. **车列事实层**:
   - release_batch 存在即可参与检装车单船名/节数拆分。
   - 95306 能确认车列时,允许先写入 `wagon_shipments` / match 表。
   - 若货运信息缺失,候选/批次标记为“车列已入库但待货运信息补齐”。
2. **发运输出层**:
   - 发运 Excel、发送、上传等动作仍要求货运信息齐备。
   - 缺计划号/合同号/货名明细时,不制作发运 Excel,不发送。

## 修复方向

- 拆分锚点不要只依赖 active rule;可考虑读取同项目非终态 release_batch 的 ship token,或直接从 `cargo_info_raw` 抽取“船名 + N节”段。
- `pending_freight` 批次在“拆分/暂存车列事实”阶段应可被引用,但在“发运 Excel/发送”阶段继续被阻断。
- 对已经挂起的旧候选,在批次从 `pending_freight -> enriched` 后应有 retroactive resplit/retry 机制,或至少在看板/工单中暴露为可处理待办。
- 保留人工闸:若船名/节数不自洽、95306 窗口不唯一、车号纠错不唯一,仍应进入人工审核。

## 验收标准

- 构造一张两船检装车单:船 A `loading/enriched`,船 B `pending_freight`,两者 release_batch 均存在。
- 系统能按单据中的船名+节数拆成两个候选。
- 95306 车列到齐后,两个候选的车列均可入库到对应 release_batch。
- 船 B 缺货运信息时不生成/发送发运 Excel;货运信息补齐后可继续生成/发送。
- 补充回归测试覆盖“后补货运信息后旧候选可继续处理”。
