# 工单：检装车图片来源收敛与 95306 合成候选去重

创建日期：2026-07-12  
项目：中唐特钢、朝阳钢铁、吉林金钢  
状态：已完成  
优先级：P1

## 现象

货运看板偶尔出现两条相同业务事件的检装车 `pending_review` / 候选。核查发现当前检装车图片并非只从“铁晟业务工作群”进入：

- 中唐特钢同时监听“铁晟业务工作群”与“中唐特钢发运群”的检装车图片；同一单据会被转发后重复建候选。
- 朝阳钢铁将“数据单发群”列为 supplemental，并允许该群的检装车图片进入候选。
- 图片尚未处理完成时，发车文本触发还会从 95306 建立 `95306_synth:*` 候选；随后真实图片候选到达时，二者可短时并存。

已核实的中唐重复样本包括：环球信任 50 车、35 车，宝丽 38 车，均在“铁晟业务工作群”和“中唐特钢发运群”中相隔数分钟入候选。

## 业务口径

1. 中唐特钢、朝阳钢铁、吉林金钢的**检装车通知单图片**业务事实源有且仅有“铁晟业务工作群”（`GROUP001`）。
2. 中唐特钢发运群仍可接收货运文本、出港计划通知单；不再触发检装车图片候选。
3. 数据单发群仍承担结果发送和补充资料职责；不再触发朝钢检装车图片候选。
4. 95306 合成候选仅是“图片未到”的临时占位。真实图片候选成功匹配后，关联合成候选必须自动 `superseded`，不允许遗留为 `candidate` / `pending_*` / `pending_review`。

## 修复目标

1. 在项目级路由和候选创建入口同时落实来源白名单，避免只改 YAML 后仍被历史/通用图片管线绕过。
2. 合成候选与真实图片候选以项目、船名、到站、车数、事件时间窗为键归并；真实图片优先。
3. 清理现有三个项目中由非 `GROUP001` 图片来源产生、且可明确对应真实图片/已完成事件的遗留候选，不改动 wagon 事实或重发外部动作。
4. 用回归测试固定：
   - 中唐发运群和数据单发群的检装车图片不建业务候选；
   - `GROUP001` 检装车图片仍正常入链；
   - 同一事件的 95306 合成候选在真实图片匹配后自动作废。

## 验收

- 三项目新的检装车图片候选均来自“铁晟业务工作群”。
- 相同事件不会因群转发或 95306 合成而出现两个待审候选。
- 原有出港计划、货运文本、发运 Excel 发送路径不受影响。
- 相关测试通过；改动后重启 live-service 与 text-watch，并检查服务状态。
