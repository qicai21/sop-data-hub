# 工单: 铁晟业务工作群历史发车文本回补装车道线

- **类型**: 功能增强 / 数据补录
- **发现日期**: 2026-07-06
- **状态**: 已处理
- **严重度**: 中

## 背景

当前 `wagon_shipments.loading_line` 的实时落库能力已经具备:

- `departure_text_parser.canonicalize_loading_line()` 已支持 `煤4 -> 煤四`、`14道 -> 十四道` 等归一。
- `create_wagon_shipments` 在检装车/文本链入库时会写入 `loading_line`。
- `text-watch` 服务在运行。

但历史数据并不完整,且共享群 `铁晟业务工作群` 中已经存在大量可用的发车文本:

- 中唐特钢: `loading_line` 已补齐到 `0` 缺失。
- 朝钢: `2200` 条中仍缺 `362` 条。
- 吉林金钢: `1108` 条中仍缺 `422` 条。
- 九三大豆: `1691` 条中缺 `1691` 条(其道线来源逻辑与共享群/内部群并行,需单独口径)。

## 现象

`铁晟业务工作群` 的历史文本并不都被正确路由为 SOP:

- 已命中 SOP 的文本确实存在,可直接利用。
- 但还有不少实际可用的历史发车消息停留在 `ignored` / `classified`,例如:
  - `煤四 汐子铁 鞍子河 57节`
  - `煤五，52节汐子铁，环球信任`
  - `煤五汐子铁 环球信任42节 马兰探险10节 共52节`

这意味着:

1. 仅扫描 `is_sop_msg=1` 的历史消息,覆盖率不够。
2. 共享群历史回补必须直接解析 `message_inbox.text_content` 原文。

## 根因

历史时期的共享群文本存在以下问题:

1. 同一业务表达方式不稳定: `煤五汐子铁环球信任55节` / `煤五，52节汐子铁，环球信任` / 混列文本并存。
2. 旧版本路由规则对白名单船名、到站词、混列格式覆盖不足。
3. 某些文本被当成“作业描述”或普通聊天而非“发车事实”,导致未进入 `matched_sop`。

## 目标

建立一条**历史文本回补链**,用于:

1. 从 `message_inbox` 提取共享群历史文本。
2. 解析出 `loading_line / destination / ship / expected_count / mixed_segments`。
3. 与 `wagon_shipments + 95306 + dispatch_train_code` 按时间窗和车数匹配。
4. 批量回填缺失的 `wagon_shipments.loading_line`。
5. 对无法唯一确定的记录输出待复核清单,不盲填。

## 建议方案

### A. 数据源

- 主表: `data/sop_agent.db.message_inbox`
- 过滤:
  - `group_name='铁晟业务工作群'`
  - `msg_type='text'`
  - 不限制 `is_sop_msg`

### B. 解析口径

统一识别:

- 道线: `煤一..煤六`、`一/二/.../十五道`、`14道` 等
- 到站/项目词:
  - 中唐: `汐子铁`
  - 朝钢: `朝阳西铁` / `乌铁`
  - 吉林金钢: `四平铁` / `凌东铁`
- 船名
- 节数
- 混列分段

### C. 回填策略

1. 先按项目筛出 `loading_line` 为空的 `wagon_shipments`。
2. 再按 `dispatch_train_code` / 制票时间窗 / 船名 / 车数去找最优文本。
3. 唯一命中则自动写回 `loading_line`。
4. 多候选或信息冲突则列入待复核。

## 验收标准

- 能从 `铁晟业务工作群` 历史文本中自动回补一批 `loading_line`。
- 自动回补只发生在唯一命中场景。
- 产出待复核清单,而不是猜填。
- 回补逻辑有固定测试覆盖:
  - 单船纯列
  - 混列拆分
  - `煤4/煤四`、`14道/十四道` 归一
  - 历史 `ignored` 文本也可参与回补

## 备注

这项工作与“未来新发车实时抓装车道线”是两件事:

- 实时链: 依赖 `text-watch + text_router + workflow chain`
- 历史链: 依赖 `message_inbox` 原始文本回扫与补录

两者都需要做,但可以分阶段交付。
